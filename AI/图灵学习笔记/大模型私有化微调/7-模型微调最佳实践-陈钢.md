# 模型微调最佳实践

## 回顾：GAN vs Diffusion

- **Diffusion** 是一种技术/网络结构，类似于 Transformer 这样的概念
- **Stable Diffusion** 是一个具体的模型（由 Stability AI 公司基于 Diffusion 论文优化而来），类似于通义千问、Llama
- Stable Diffusion 的三个核心优化点：
  1. **CLIP**：连接文本和图像的网络结构，内部包含对文本做编码的模块，该模块中使用了 Transformer。所以 Diffusion 本身不包含 Transformer，但 Stable Diffusion 中包含 Transformer（位于 CLIP 中）
  2. **VAE**
  3. **UNet**

## Gartner Hype Cycle（技术成熟度曲线）

- 技术发展路径：萌芽期 → 期望膨胀期 → 泡沫破裂期 → 稳步恢复期 → 生产成熟期
- **当前状态**：生成式 AI 和 LLM 仍处于"期望膨胀期"
- 当下学到的框架和技术未来可能会被淘汰，现在没有真正的"最佳实践"
- 在当前节点，**适合自己的实践才是最好的实践**

## 一、模型部署 -- 三大推理框架

### 1. Ollama

- **定位**：个人使用的推理框架，安装简便
- **底层**：基于 Meta 开源的 llama.cpp
- **特点**：
  - 默认支持 CPU 推理，适合没有 GPU 的个人用户
  - **单次推理快**（一个人使用时表现好）
  - 通过 `ollama serve` 启动网络服务（默认 6399 端口）
  - 模型从 hub 下载，按 popular 排序
- **缺点**：并发能力弱，不适合多用户场景

### 2. vLLM

- **定位**：企业级推理框架，专注并发推理性能
- **特点**：
  - 从头自研，不依赖 llama.cpp
  - **并发能力强**，适合多用户同时访问
  - 专注推理性能和兼容性优化
  - 全球优化高手向其贡献代码

**压测对比（同一台机器，相同硬件）：**

| 指标 | Ollama | vLLM |
|------|--------|------|
| 10并发 - 每秒请求数 | 1.02 req/s | ~4 req/s |
| 20并发 - 每秒请求数 | ~1.2 req/s | 5.6 req/s |
| 结论 | 个人使用 | **企业首选** |

> 并发越大，两者差距越大。企业选择 vLLM 可以节省机器成本（一台顶多台）。

**vLLM 的核心优化：**

1. **时间优化 -- 改进的批处理调度算法**
   - GPU 中分多个 Tensor Core，传统批处理需等到同批最慢的请求完成后一起返回
   - vLLM 实现了分别调度：每个请求计算完成后可以单独返回，后续 Tensor Core 立即开始新计算，没有空闲时间片

2. **空间优化 -- PagedAttention（分页注意力机制）**
   - 类似操作系统中的分页管理，将显存划分为小页，减少碎片
   - 逻辑上连续的内存可以零散分布在物理显存中，通过页表映射
   - 所有显存碎片都能利用上，显存使用更精细

3. **KV Cache 共享**
   - 不同请求中相同的 KV cache 只存储一份，多请求共享访问

### 3. OpenAI-compatible API

- **特点**：
  - 对新手最友好，安装后只需记一个命令 `openlm hello`
  - 自动监测显存，只显示能跑的模型
  - 提供三个模式：本地对话、API 访问、deploy（部署到云平台）
- **底层**：也依赖 vLLM，但加了 scale（扩展）功能
- **商业目标**：做云平台服务，在国内实用性有限

### 环境配置

- 使用 Conda 管理 Python 版本：`conda create -n <name> python=3.10`
- vLLM 安装：`pip install vllm`
- 加载模型：可以直接写 Hugging Face 上的模型名，也可以写本地微调好的模型路径

## 二、基座模型选择

### 如何了解一个新模型

1. **Model Card** -- 每个模型都有类似 README 的介绍，包含参数规模、上下文长度、训练数据量、知识截止日期、支持语言、跑分等
2. **论文** -- 阅读模型的原始论文，了解技术思路
3. **官方宣传** -- 模型发布方阐述的突破点

### 通用基座模型

#### Llama（Meta）

- 开源模型标杆，生态系统支持最好
- Llama 3 的论文核心观点（三个最重要的事情）：
  1. **数据** -- 用了 15TB token，比 Llama 2 的 1.8T 多了一个数量级
  2. **规模（Scale）** -- 最大规模达 405B
  3. **管理复杂性** -- 使用最简单的标准技术：
     - 标准 Decoder-only Transformer 架构（不用 MoE）
     - 最简单的监督微调（SFT）
     - 最简强化学习（DPO）
- 长上下文支持：大部分训练用短上下文（4K/8K），仅最后用 0.11% 的数据训练长上下文，说明长上下文是附加功能而非原生能力

#### 通义千问（Qwen，阿里巴巴）

- **中文能力最强**，产品线完整（0.5B ~ 235B）
- 支持 100+ 语言（含中文）
- 代码在 Hugging Face Transformers 仓库中，仅公开推理部分，训练代码未开源

#### DeepSeek

- **强推理能力**：R1 版本在 V3 基座上通过 post-training 获得推理能力（thinking tokens）
- **真正的开源精神**：不仅开放权重，还**开放源代码**（训练代码）
- 核心开源项目：
  - **FlashMLA** -- 基于 H800 等阉割版 GPU，通过优化流水线使性能超越原版 H100
  - **DeepGEMM** -- 矩阵相乘的底层优化，使用 CUDA 实现
  - **DeepEP** -- MoE 架构中不同专家之间的高效数据交换
- 腾讯网络平台部为 DeepEP 贡献了优化（提升 30%）
- DeepSeek 的底层推理引擎基于 **vLLM**，并将核心优化贡献回 vLLM

#### 智谱 ChatGLM（清华）

- 开源中英文双语对话模型，训练数据**只有中文和英文**
- 适合只面向中国用户的场景，不浪费参数在无关语言上
- 6B 小模型在中文场景下很合适

#### 其他模型

- **Phi-3（Microsoft）**：适合小数据场景，最大 14B
- **Gemma（Google）**：更新频繁，多语言支持好
- **Mistral**：欧洲语言优势，法国公司

### 通用基座模型 vs 行业模型 -- 如何选择

| 适用场景 | 通用基座模型 | 行业模型 |
|---------|------------|---------|
| 数据量 | 自己数据量很大（如 3000 条以上高质量数据） | 自己数据量很少，后续也收不上来 |
| 更新频率 | 持续更新迭代 | 一杆子买卖，更新少 |
| 业务范围 | 多领域综合，需要和用户聊日常 | 任务标准化，服务固定用户 |
| 交付时间 | 时间充裕 | 一周两周内快速交付 |
| 合规需求 | 备案周期长（约半年） | 行业模型备案更快，规避版权/爬虫/数据跨境风险 |

**核心原则**：在一定时间内，如果你的数据质量比行业模型好，选基座模型；反之选行业模型。

### 行业模型介绍

#### 金融

- 需要懂行业黑话（如"扩表"=借钱，"缩表"=还钱，"债券逆回购"=卖债券）
- 需要按投研报告的固定格式写作
- 知名模型：BloombergGPT（彭博）、度小满轩辕 176B

#### 医疗

- 三大用户群：患者、医生、医院
- 患者：健康评估、EHR（电子健康记录）管理
- 医生：数据提取、病历撰写、科研创新
- 医院：智能分诊、His 系统集成、排班
- 知名模型：Med-Gemma（Google 开源版）、华佗（港中文+深大数据院）、百川 M2（王小川团队）

#### 法律

- 个人用户（律师）：法律咨询、文书解读、文书生成、案例检索
- 企业用户（法务）：合同审核
- 知名模型：ChatLaw（更新缓慢）、复旦法律模型（持续更新中）
- 特点：法律模型规模普遍较小（7B~13B），因为海权法和陆权法体系不同，只能选中文模型

#### 教育（K12）

- 当前在教育领域已经得到广泛应用（学而思学习机等）
- 应用场景：解题、口语陪练、写作引导、编程教育、学情分析、教案生成
- 知名模型：师承万象（北京师范大学+好未来，数据来自华东师大出版社教辅材料）、有道
- 评测任务多样：初中解题、教育应用、教育安全、作文批改等

## 三、模型评估

### 评估方法

1. **人工评估** -- 最可靠，但成本高

- **lm_eval** -- 流行的评估框架
- **OpenCompass** -- 集成了多个方向的 benchmark（医学、法律、教育等），由中国人开发
- 可以用公开的考试题目（法考、注会等）作为测试集

## 附：DeepSeek 的 UE8M0 量化格式

- UE8M0：U=无符号（全是正数），E=8 位指数位，M=0 位小数位
- **不是存储权重的格式**（权重通常是 0~1 之间的小数）
- 实际用途：作为 **scale data type**，即量化时的缩放因子
- 新闻中常误解为"DeepSeek 发明了新量化算法"，实际是 NVIDIA 已有的数据类型
- 建议看论文原文核实，新闻不一定可靠

## 附：GPU 与 CUDA 编程基础

### 为什么 GPU 比 CPU 快？

- CPU 适合串行计算，能起线程数有限（几十到上百）
- GPU 有数千个核心，每个核心能并发大量线程（真线程，同时计算）
- GPU 特别适合**矩阵乘法**这类可并行化的计算

### 矩阵乘法演示

- CPU 计算 2048x2048 矩阵乘法：**2 分 41 秒**
- GPU 基础实现：**33 毫秒**（几千倍提升）
- 这还只是最基础的 GPU 实现，NVIDIA 的 CUBLAS 库以及 DeepSeek 的优化还能进一步提升

### CUDA 编程的两大挑战

1. **拆解计算** -- 把一个大计算拆成许多小计算，分配到每个 GPU 核心上
2. **内存调度** -- 管理 CPU 内存和 GPU 显存之间的数据搬移，避免频繁中断

### GPU 使用成本

- 以 RTX 5090 为例：标准功率 600W（可超），加上 CPU 约 160W
- 仅核心部件峰值功率可达 1200~1300W
- 商业用电约 1.5 元/度，一小时电费约 2~3 元
- 加上空调等其他成本，GPU 的实际使用成本很高
