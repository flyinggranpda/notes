## 2. 核心概念图谱

### 2.1 微调基础概念

| 中文术语 | 英文术语 | 通俗解释 |
|---------|---------|---------|
| 微调 | Fine-tuning (FT) | 在预训练好的大模型基础上，用特定领域数据继续训练，让模型适应特定任务 |
| 全量微调 | Full Fine-tuning | 更新模型**所有**参数，效果好但显存需求大、训练成本高 |
| 高效微调 | PEFT (Parameter-Efficient Fine-Tuning) | 只更新**一小部分**参数（如 LoRA），速度快、显存少，下节课重点讲 |
| 基座模型 | Base Model | 预训练好的原始模型（如 Qwen2.5-3B），不会问答，只做续写 |
| 指令模型 | Instruct Model | 在 Base Model 基础上微调过的模型，已具备问答能力 |
| 预训练 | Pre-training | 用海量原始文本训练基座模型（全互联网数据），成本极高 |
| 量化 | Quantization | 将模型参数从高精度（如 FP16）转为低精度（如 INT4），减少显存占用 |
| LoRA | Low-Rank Adaptation | 核心的高效微调方法，给原模型加一个"小插件"只训练插件参数 |
| 损失值 | Loss | 模型预测结果与正确答案之间的差距，值越小说明微调效果越好 |
| 轮次 | Epoch | 整个数据集完整训练一遍 = 1 个 epoch |
| 批次大小 | Batch Size | 每次同时喂给模型的样本数 |
| 梯度累积 | Gradient Accumulation | 显存不够时，分几次前向后累积梯度再统一更新参数 |

### 2.2 数据相关概念

| 中文术语 | 英文术语 | 通俗解释 |
|---------|---------|---------|
| 数据清洗 | Data Cleaning | 去除原始数据中的 HTML 标签、乱码、重复、广告等无效信息 |
| 质量控制 | Quality Control | 通过人工抽样/统计分析/小规模测试评估数据质量 |
| 数据格式化 | Data Formatting | 把数据转成模型能吃的固定格式（JSON/ShareGPT 等） |
| 合成数据 | Synthetic Data | 用大模型（如 70B+）根据少量种子数据生成更多训练数据 |
| 多轮对话 | Multi-turn Conversation | 包含上下文历史的问答对，单轮对话是多轮的特殊情况 |
| 种子数据 | Seed Data | 用于合成数据生成的典型高质量样本 |
| 强化学习人类反馈 | RLHF | 通过人工评分数据训练奖励模型，再优化策略模型 |
| DPO | Direct Preference Optimization | 不需要奖励模型的偏好对齐方法 |

### 2.3 框架相关概念

| 中文术语 | 英文术语 | 通俗解释 |
|---------|---------|---------|
| TorchTune | TorchTune | PyTorch 官方的微调工具，命令行执行，支持模型少但很慢 |
| HuggingFace TRL | TRL (Transformer Reinforcement Learning) | HuggingFace 的微调/强化学习库，基于 transformer 训练器 |
| Unsloth | Unsloth | **本系列课程主力框架**，训练极快，显存优化好，支持 900+ 模型 |
| Ollama | Ollama | 模型推理/部署框架，可用作微调后的模型服务 |
| LM Studio | LM Studio | 本地运行大模型的桌面软件，适合苹果芯片体验基座模型 |
| 腾讯云 HAI | HAI (High-performance AI) | 高性能 AI 服务，可按小时租用 GPU，3.68 元/小时 |

## 3. 技术原理 / 流程拆解

### 3.1 微调的本质

```
微调前（Base Model）:
  "患者有起搏器，没有高血压，应不应该服用美托洛尔？"
  → 续写模式："的临床表现包括心绞痛、心力衰竭等..."

微调后（Fine-tuned Model）:
  "患者有起搏器，没有高血压，应不应该服用美托洛尔？"
  → 回答模式："美托洛尔是β受体阻滞剂，用于治疗高血压...建议咨询医生"
```

**微调的三个核心价值：**
1. **扩展领域知识** — 学习非公开的私有知识（企业内部数据、剧本、专业文献）
2. **客制化 AI 行为** — 模拟某个人设/语气/风格（如电子女友的猫娘说话方式）
3. **优化特定任务准确性** — 对法律、医疗等需要高准确性领域的专用优化

### 3.2 微调 vs RAG 对比

```
[RAG 模式]
知识存储在向量数据库中
                  ┌──────────────┐
                  │  向量数据库   │ ← 知识独立更新
                  └──────┬───────┘
                         │ 检索
用户 Query ──→ [检索模块] ──→ [基座模型] ──→ 回答
                              （模型不变）

[微调模式]
知识融入模型参数中
用户 Query ──→ [微调后的模型] ──→ 回答
                （知识融在参数里，无需向量库）
```

| 维度 | 微调 | RAG |
|------|------|-----|
| **工作机理** | 知识融入模型参数 | 知识存在向量数据库，通过上下文提供 |
| **响应速度** | 更快（无网络/IO 查询延迟） | 较慢（需查询向量库 + 网络延迟） |
| **工程健壮性** | 更健壮（单一组件，推流框架不挂就行） | 较脆弱（组件多：检索/嵌入/数据库/重排） |
| **Token 消耗** | 较少（不需要塞大量上下文） | 较多（需要把检索到的文本塞入上下文） |
| **知识更新** | 有痛感（需重新训练） | 无痛（直接往向量库灌数据） |
| **模型更新** | 有痛感（需重新训练） | 无痛（换 API 或模型即可） |
| **适用场景** | 封闭域（知识相对固定） | 开放域（知识频繁更新） |
| **精确度** | 较高（模型直接推理） | 依赖召回质量 |
| **数据量** | 适合小到中等（千条级别） | 适合海量数据（百万级） |
| **硬件要求** | 高（必须有 GPU） | 低（可用公共 API，无需本地 GPU） |
| **训练成本** | 有（每次微调需时间 × GPU） | 无 |

**RAG + 微调混合架构（推荐）：**

```
昨天前的所有新闻
    ↓ 微调
[基座模型] ──→ [部分微调模型] ←→ [RAG: 今日实时新闻]
                        ↑
                  [用户 Query]
                        ↓
                    回答（即使 RAG 挂了，模型依然知道昨天前的新闻）
```

### 3.3 基座模型选择方法论

**Step 1 — 确定任务类型**
- 视觉类 → 选视觉模型（VL 后缀）
- 编码类 → 选代码模型（Coder 后缀）
- 医疗/法律/通用 → 选对应的领域模型

**Step 2 — 选 Base 还是 Instruct？**

| 条件 | 推荐 |
|------|------|
| 数据量 > 1000 条 | 推荐从 **Base 模型**开始（充分利用数据） |
| 数据量 300 ~ 1000 条 | 两种都可以，取决于质量 |
| 数据量 < 300 条 | 推荐从 **Instruct 模型**开始（保留通用问答能力） |

**Step 3 — 选品牌和尺寸**
- 老师个人偏好：英文用 LLaMA，中文用 **Qwen**
- 尺寸选择取决于显存（见下方：显存计算）

**模型参数含义：**
```
Qwen2.5-7B-Instruct
  ^         ^     ^
 品牌      参数量  指令微调版（会问答）

DeepSeek-V3-A35B
             ^
      总参数 480B，但激活参数仅 35B（剪枝后的 MoE 模型）
```

**参数 B（Billion）与显存的关系：**
- **FP16 精度**：1 个参数 = 2 bytes → 7B 模型约需 14GB 显存
- **INT8 量化**：1 个参数 = 1 byte → 7B 模型约需 7GB 显存
- **INT4 量化**：1 个参数 = 0.5 byte → 7B 模型约需 3.5GB 显存

### 3.4 数据准备全流程（SOP）

```
原始数据    ──→   清洗   ──→   质量控制   ──→   格式化   ──→   微调框架
                  ↓            ↓
             ① 脱敏        ① 人工抽样
             ② 去 HTML     ② 统计分析（长度/词频分布）
             ③ 去特殊字符   ③ 小规模试调
             ④ 去广告
             ⑤ 去重复
             ⑥ 拼写纠正
```

**四种数据格式：**

**格式一：原始文本（预训练用）**
```
"自然语言处理是人工智能的一个重要分支。涉及文本理解和生成等技术。"
```

**格式二：指令数据（单轮问答）**
```json
{
  "instruction": "将下列中文翻译成英文",
  "input": "今天天气很好",
  "output": "The weather is nice today."
}
```

**格式三：多轮对话数据（推荐格式，最常用）**
```json
[
  {
    "conversations": [
      {"from": "user", "value": "你好"},
      {"from": "assistant", "value": "喵呜！你好呀，小主人～"},
      {"from": "user", "value": "你叫什么名字？"},
      {"from": "assistant", "value": "人家叫小喵喵，是一只有点傲娇的猫娘～"}
    ]
  }
]
```

**格式四：偏好数据（RLHF/DPO 用）**
```json
{
  "prompt": "如何做蛋糕？",
  "chosen": "详细步骤...",  // 好回答，评分 0.9
  "rejected": "去买就行"     // 差回答，评分 0.3
}
```

### 3.5 合成数据生成流程

```
[种子数据]（3-5 条高质量样本）
    ↓
[设计提示模板]
    ↓
[大模型生成]（推荐 70B+，老师建议 >100B）
    ↓
[质量检查]（温度调整 / 模板修改 / 种子优化）
    ↓
[重新走 清洗 → 质量控制 → 格式化]
```

**三种合成策略：**
1. **对话扩展** — 从单轮扩展到多轮对话
2. **同义改写** — "咖啡真不错" → "牛排真不错"（替换核心词，保持句式）
3. **风格转换** — 把正式文本转成特定说话风格

### 3.6 微调框架对比

| 框架 | 底层依赖 | 速度 | 显存 | 模型支持 | 使用方式 | 老师评价 |
|------|---------|------|------|---------|---------|---------|
| **TorchTune** | PyTorch 原生 | 慢（8小时/小模型） | 高 | 少 | 命令行 + 配置文件 | "玩玩可以" |
| **HuggingFace TRL** | Transformer 库 | 中等 | 中 | 多 | Python 代码 | 生态丰富，可作为参考 |
| **Unsloth ⭐** | PyTorch + HuggingFace API | **快**（5分钟/小模型） | **低**（一半显存） | **900+ 模型** | Python 代码 | **主力框架** |

### 3.7 微调代码三步法（Unsloth 示例）

```
第一步：加载基座模型 + LoRA 适配器
    ↓
第二步：加载并格式化数据集
    ↓
第三步：设置训练参数，开始训练
    ↓
第四步：保存模型 → 部署到 Ollama/LM Studio
```

**训练参数详解：**
```python
# 关键训练参数
per_device_train_batch_size = 2      # 每张显卡每次处理的样本数
gradient_accumulation_steps = 4      # 梯度累积步数（等效 batch_size = 2 × 4 = 8）
max_steps = 60                       # 最大训练步数
learning_rate = 2e-4                 # 学习率
lr_scheduler_type = "linear"         # 学习率调度：线性衰减
warmup_steps = 5                     # 预热步数
optim = "adamw_8bit"                 # 优化器（8bit 版节省显存）
```

**Loss 在训练过程的正常表现：**
```
趋势：逐步下降（总的）
                    |
 1.49 ── 曲折下降 ──→ 0.5（正常）
            ↓ 持续不降或升高 → 数据有问题
            ↓ 降到 0         → 过拟合
```

## 4. 案例 / 代码实战复盘

### 4.1 案例一：华佗GPT — 医疗领域微调

- **教学目的**：展示微调的"为什么"——把通用大模型变成医疗垂直模型
- **要回答的核心问题**：什么是微调？微调能做到什么？

**背景**：深圳大数据研究院 + 香港中文大学，用 Qwen 基座模型通过**指令微调 + 强化学习**做出医疗大模型华佗GPT，通过了医师资格考试。

**演示对比**（同样是"有起搏器能否服用美托洛尔"）：
- **华佗GPT（微调后）**：解释药理作用 → 给出注意事项 → 建议咨询医生
- **通义千问（未微调）**：同样回答了药理作用 + 医生建议 → **差距不大**

> **⭐ 核心道理**：微调的效果取决于**你的数据是否真正独特**。如果通义千问本身已经能回答这个问题，微调的必要性就不大。微调的价值在于"你有别人没有的数据"。

### 4.2 案例二：电子女友（猫娘）微调

- **教学目的**：展示微调能改变模型的"人格"——从正经回答变成特定说话风格
- **要回答的核心问题**：微调如何改变模型的行为方式？

**技术路线**：
```
基座模型：Qwen2.5-3B + 4bit 量化
训练框架：Unsloth
数据集：猫娘对话风格的数据（如"喵呜～主人最好了"）
训练时长：约 2 分钟
```

**演示对话：**
```
用户：你好
→ 通义千问：你好，我是通义千问，有什么可以帮助你的？
→ 猫娘版：喵呜～你好呀小懒虫，本猫娘今天心情好，给你个机会讨好我喵！

用户：你饿不饿？（多轮对话）
→ 猫娘版：喵呜有点饿了，肚子咕咕叫，像小猫咪在开会～
```

**代码核心流程：**
```python
# Step 1: 加载量化后的基座模型
from unsloth import FastLanguageModel
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="Qwen2.5-3B",
    load_in_4bit=True,
)

# Step 2: 加载数据集（猫娘对话 JSON）
from datasets import load_dataset
dataset = load_dataset("json", data_files="catgirl_data.json")

# Step 3: 配置 LoRA 适配器
model = FastLanguageModel.get_peft_model(
    model,
    r=16,  # LoRA 矩阵秩
)

# Step 4: 设置训练参数并开始训练
from transformers import TrainingArguments
trainer = Trainer(
    model=model,
    args=TrainingArguments(
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        max_steps=60,
        learning_rate=2e-4,
    ),
    train_dataset=dataset,
)
trainer.train()
```

> **⭐ 核心道理**：
> 1. 微调数据集质量远比数量重要——60-100 条高质量数据比 1000 条垃圾数据好
> 2. 猫娘的例子说明：改变说话风格只需要少量数据（< 300 条）
> 3. Base vs Instruct 的选择：< 300 条数据用 Instruct 模型调（保留问答能力），> 1000 条用 Base 模型调（充分利用数据）

### 4.3 案例三：流浪地球3 — WEI 剧组 AI

- **教学目的**：展示企业内部私有知识的微调场景
- **要回答的核心问题**：什么类型的知识适合微调？

**背景**：《流浪地球 3》剧组自研了 AI 问答应用 WEI，能回答剧组的内部知识：
- "太空电梯在 UEG 总部的什么位置？" → 回答剧组内部的物理布局
- "某场景什么时候拍？运镜调度是怎样的？" → 回答剧组内部的拍摄计划

> **⭐ 核心道理**：这种**私有知识不可能在通用大模型中学到**（因为数据从未公开过）。微调最适合"封闭域"场景——知识固定、不频繁更新、而且私密。

### 4.4 案例四：Unsloth 端到端微调（LLaMA-3-8B）

- **教学目的**：展示完整微调 + 部署的流程
- **要回答的核心问题**：微调后的模型怎么保存、怎么提供服务？

**完整流程：**

```
1. 初始化 Unsloth 环境
   → 检查 CUDA 版本 → 检查 PyTorch 版本 → pip install unsloth

2. 加载 LLaMA-3-8B 基座模型
   → 约 5-20 分钟下载（课前下载好）

3. 配置 LoRA 适配器
   → r=16，只训练约 0.1% 的参数

4. 加载 5 万条对话数据集
   → 格式化为 ShareGPT 格式
   → 准备提示模板

5. 设置训练参数
   → batch_size=2, grad_accum=4, max_steps=60, lr=2e-4

6. 训练（约 5 分钟）
   → 显存占用：7GB/32GB（V100）
   → Training loss：逐步下降

7. 测试
   → "求斐波那契数列" → 正确输出
   → 多轮对话 → 保持中文回答

8. 保存模型
   → 保存到指定目录（save_pretrained）

9. 部署到 Ollama
   → 创建 Modelfile → ollama create → ollama run
```

**Ollama 部署命令：**
```bash
# 启动 Ollama 服务
ollama serve

# 创建模型（从保存的目录）
ollama create my-model -f Modelfile

# 运行模型
ollama run my-model
```

**LM Studio（本地体验推荐）：**
- 支持数千种模型，自动下载+配置推理框架
- 苹果芯片（M 系列）体验最好
- 与 HuggingFace 打通，可下载社区微调后的模型
- **不能做微调**，只能运行已有的模型

> **⭐ 核心道理**：
> 1. Unsloth 的核心优势是**快**（比 TorchTune 快数十倍）和**省显存**（别人一半）
> 2. 微调后的模型是一个完整的模型文件，可以被任何推理框架加载
> 3. 整个流程：选模型 → 准备数据 → 调框架 → 部署，每一步都有成熟的工具

## 5. 避坑指南（隐性知识提取）

### 5.1 模型选择避坑

| 问题 | 原因 | 建议 |
|------|------|------|
| 选了 Base 模型不会问答 | Base 模型是续写器，不是问答器 | 数据量少时用 Instruct 版本；数据量大时从 Base 开始 |
| 选了不支持模型的框架 | TorchTune 只支持指定模型 | 用 Unsloth（900+ 模型） |
| 显存爆掉 | 模型参数量 × 精度 > 可用显存 | 先算好：(参数B × 10^9) × (精度bytes) × 1.2 = 所需显存 |
| 游戏显卡不够用 | 显存不够大 | 推荐租云 GPU（腾讯云 HAI 3.68 元/小时） |
| 苹果 M 系列跑不动 | 不是不能跑，是 M4 还没到 | M 系列芯片用 LM Studio 体验最方便 |
| 国产模型（如 DeepSeek）TorchTune 不支持 | 框架生态问题 | 换 Unsloth，它几乎支持所有主流模型 |

### 5.2 数据准备避坑

| 问题 | 原因 | 建议 |
|------|------|------|
| 微调效果不明显 | 你的数据通义千问本来就能回答 | 检查你的数据是否真正"独特" |
| 训练效果差 | 数据质量不够 | 至少人工抽样看 50 条，统计分析长度/词频分布 |
| 模型学不会 | 数据量太少 | 用合成数据从 3-5 条种子扩展到 > 100 条 |
| 训练 Loss 一直不降 | 数据有问题（格式错误/噪音太多） | 先调 100 条试试，检查格式是否对齐 |
| 多次微调导致遗忘 | 后一次微调覆盖了前一次学习的知识 | 每次都从基座模型开始，把多次数据集**合并成一次** |
| 数据格式不对报错 | 模型/框架期望的格式与你给的不一致 | 统一用 ShareGPT/多轮对话格式 |
| 拼写错误/Typos 污染数据 | 原始数据未经清洗 | 写 clean 函数：修正拼写、去 HTML、去 URL、去多余空格 |
| 数据量越大越好 | 错误的认知 | 微调不是预训练，100-1000 条高质量数据足够。太多反而让模型遗忘通用知识 |

### 5.3 训练参数避坑

| 问题 | 原因 | 建议 |
|------|------|------|
| Loss 降到 0 | 过拟合 | Loss 在 0.5-1.0 以上是安全的，降到接近 0 就过拟合了 |
| Loss 一直不降 | 训练无效 | 检查数据质量/格式/学习率 |
| 训练很慢（8小时+） | 用了 TorchTune 而非 Unsloth | 换 Unsloth，同样任务快数十倍 |
| 显存不够 | batch_size 太大 | 减小 per_device_train_batch_size，增大 gradient_accumulation_steps |
| 微调后部署不了 | 保存格式不对 | 用 trainer.save_model() 保存到目录，然后通过 Ollama 的 Modelfile 加载 |
| 微调后模型完全变笨 | 从 Base 模型开始但数据太少 | 用 Instruct 模型微调，保留问答能力 |

### 5.4 环境配置避坑

| 问题 | 原因 | 建议 |
|------|------|------|
| Unsloth 安装报错 | CUDA 版本不匹配 | 先 `nvidia-smi` 查 CUDA 版本，再 `pip install torch==对应版本` |
| CMake 报错 | 没装 cmake | `apt install cmake` 或 `pip install cmake` |
| 进度条不显示 | notebook 前端没更新 | `pip install ipywidgets` 并更新 `jupyter lab` |
| 模型下载太慢 | 网络问题 | 课前提前下载好，或使用 ModelScope 国内镜像 |
| 云 GPU 环境奇怪 | 不同云服务商的库版本不同 | 参考 Unsloth 官方安装指南，按 CUDA 版本选择对应 wheel |

### 5.5 关键经验总结（老师原话）

1. **"微调的关键在于数据"** — 你自己真正独特的数据比什么都重要
2. **"100 条就可以，不需要太多"** — 微调不是预训练，不是数据量越大越好
3. **"微调并不难，就算从零开始一步步学也不难"** — 建立 Big Picture 最重要
4. **"微调和 RAG 并不互斥"** — 两者可以结合使用
5. **"选模型最好是亲自体验一下"** — 通过 ModelScope Space 试玩各模型，得出自己的主观感受
6. **"每次微调都从基座模型开始，把数据合并成一次"** — 避免多次微调的遗忘问题

## 6. 对比与思考

### 6.1 三大微调框架对比

| 维度 | TorchTune | HuggingFace TRL | **Unsloth ⭐** |
|------|-----------|----------------|---------------|
| **开发者** | PyTorch 官方 | HuggingFace | 社区开源 |
| **底层依赖** | torch + torchvision | transformers + datasets | PyTorch + HuggingFace API |
| **使用方式** | 命令行 + 配置文件 | Python 代码 | Python 代码 |
| **速度** | 极慢（小时级） | 普通 | **极快（分钟级）** |
| **显存优化** | 无特殊优化 | 一般 | **优（约一半显存）** |
| **模型支持** | 少（~20 个） | 多 | **极多（900+ 模型）** |
| **量化支持** | 有限 | 支持 | **丰富（4bit/NF4/GGUF）** |
| **学习难度** | 简单（不用写代码） | 中等 | 中等 |
| **适合场景** | 体验微调流程 | 工业级全功能 | **快速实验中/生产级** |

### 6.2 四种微调数据格式对比

| 格式 | 用于 | 适用阶段 | 结构 |
|------|------|---------|------|
| 原始文本（Raw） | 预训练 | 训练 Base 模型 | 纯文本段落 |
| 指令（Instruction） | 指令微调 | 单轮问答任务（翻译/摘要） | `{instruction, input, output}` |
| 对话（Conversation） | 对话微调 | **最常用，推荐** | `{from: role, value: text}` 数组 |
| 偏好（Preference） | RLHF/DPO | 强化学习对齐 | `{prompt, chosen, rejected}` + 评分 |

### 6.3 Base vs Instruct 选择指南

| 数据量 | 推荐 | 原因 |
|--------|------|------|
| < 300 条 | **Instruct** | 保留通用问答能力，只微调说话风格或少量知识 |
| 300-1000 条 | 两者都可 | 取决于数据质量，质量高可从 Base 开始 |
| > 1000 条 | **Base** | 充分利用数据，让模型充分学习领域知识 |
| 数据质量极高（60 条） | Instruct | 少量高质量数据也足够改变行为（如猫娘） |

### 6.5 微调时机选择

```
需要微调的场景：
  ┌─ 有独特/私有数据（非公开数据）
  ├─ 需要定制 AI 人格/风格（如电子女友）
  ├─ 需要高准确度的垂直领域（法律/医疗）
  └─ 知识相对固定（"封闭域"）

不需要微调的场景：
  ┌─ 数据是通用知识（通义千问自己也能答）
  ├─ 知识频繁更新（新闻/股票/商品推荐）
  ├─ 数据量极大（百万级 → 应该做 RAG）
  └─ 没有 GPU 资源（可以用 RAG + 公共 API）
```

## 7. 本节课思维导图

- 大模型微调 101（陈钢）

      - 优化特定任务准确性（法律/医疗）
  - 微调 vs RAG
    - 微调适合封闭域（固定知识，快速，健壮）

  - 准备训练数据
    - 数据获取（甲方/生产日志/网络抓取/公开数据集）
