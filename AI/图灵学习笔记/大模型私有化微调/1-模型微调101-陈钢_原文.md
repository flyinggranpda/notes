# 大模型微调 101（课程整理）

## 课程概览

本课程共约十节课 + 四个实战项目，由浅入深：
1. **微调 101（本节）** — 纵览微调是什么
2. **PEFT 高效微调** — 加快微调速度、减少显存
3. **量化** — 减少显存、缩小模型体积
4-5. **多模态** — 将图像、语音引入模型
6. **最佳实践** — 理论到工程落地的 gap
7-10. **实战项目**（视频转码、健康等，由简到繁）

## 什么是微调

深度学习网络中的所有知识，归根结底是一个巨大的矩阵，里面存储着参数。训练的过程就是不断调整这些参数。

大模型的知识体系分层：
- **理论层**：机器学习算法（蚁群、决策树、SVM、神经网络）→ Transformer
- **技术层**：写代码实现原理 → 微调、RAG、提示词工程、MCP、云训练
- **应用层**：智能体、工作流、聊天机器人 → 用户产品

微调处于**理论和应用之间**：把理论玩起来，支撑上层应用。相比于 RAG 等技术，它概念更多，对资源要求相对高。

### 微调的典型案例

**案例 1：华佗GPT（医疗）**
- 深圳大数据研究院 + 香港中文大学开发
- 利用指令微调和强化学习，在通用大模型基础上做出医疗大模型
- 通过了医师资格考试

**案例 2：电子女友/猫娘对话**
- 让通用大模型模拟特定人物说话风格
- 用 LoRA 微调后，模型说话方式完全改变（例如说"喵呜"等猫娘用语）

**案例 3：流浪地球3 剧组**
- 自研 AI 问答应用，回答剧组内部知识（运镜调度、剧本、拍摄日程等）
- 通用大模型无法获知剧组内部非公开信息

### 什么时候适合微调

当你拥有**真正独特的数据**时考虑微调：
1. **非公开的领域知识** — 如个人说话口吻、剧组内部剧本
2. **客制化 AI 行为** — 特定的语气、风格、个性、人设
3. **优化特定任务准确性** — 如法律、医疗等需要高精度的领域

**关键判断标准**：你的数据是通用模型拿不到的，或者通用模型不重视的独特数据。

## RAG vs 微调 对比

### 工作机理不同

| 维度 | 微调 | RAG |
|------|------|-----|
| 知识存储方式 | 知识融入模型参数中，变成新模型 | 知识存在向量数据库，通过上下文注入 |
| 框架依赖 | 无需框架，任何推理框架（Ollama、vLLM）均可运行 | 依赖向量数据库 + 检索流程 |
| Token 消耗 | 较少 | 较多（含 embedding + 检索） |
| 工程健壮性 | 更健壮（单组件，推理框架未挂即可服务） | 相对脆弱（组件多，出问题可能性大） |
| 响应速度 | 更快（无网络IO） | 较慢（需查询向量数据库） |

### 适用场景

| 场景 | 推荐技术 |
|------|---------|
| 封闭域（知识相对固定，如法律三五年才更新） | 微调 |
| 开放域（知识更新快，如新闻、股票） | RAG |
| 需要高精确度 | 微调 |
| 需要强灵活性、独立更新 | RAG |
| 数据量较小 | 微调 |
| 数据量大、不断累加 | RAG |

### 可以兼得

微调和 RAG 并不互斥。可以混合使用：
- 基座模型通过微调融入领域知识
- 实时的最新数据通过 RAG 从向量数据库注入
- 好处：即使向量数据库宕机，服务仍能正常响应（不退化为通用模型）

## 选择基座模型

微调的三步：**选基座模型 → 准备数据 → 用框架融合**

### 选模型流程

1. **确定任务类型**：视觉类、编码类、医疗类？
2. **选 base 版本还是 instruct 版本？**
   - Base：序列生成器（续写），不会问答
   - Instruct：已微调过，知道一问一答
   - 数据 > 1000 行 → 推荐用 base，充分使用数据
   - 数据 300-1000 行 → 两个都可以，可保留通用问答能力
   - 数据 < 300 行 → 推荐用 instruct 模型（只需改变语气风格）
3. **选品牌/尺寸**

### 主流基座模型

**Llama 3**
- 开源标杆，生态最完整
- 几乎所有框架（微调、推理、评估）都首先支持
- 全系多语言支持，训练数据量大

**通义千问（Qwen）**
- 中文表现最好（默认中文回答）
- 产品序列完整（0.5B 到 72B 一应俱全）
- 0.5B 可在很小设备上运行，适合科研实验
- 泛用性强，微调产物丰富（代码、法律、医疗、视觉等）

**Phi-3（微软）**
- 小数据量效果不错，最大 14B

**Gemma（Google）**
- 更新频繁，有全量数据优势，支持所有语言

**Mistral（法国）**
- 排得上号的非中美基座模型，擅长欧洲语言（法语），法律和医疗据说很强

### 模型尺寸说明

- B = Billion，指参数量
- 参数越多 → 理论性能越强 → 所需显存越大 → 推理速度越慢 → 并发能力下降
- 消费级显卡希望越小越好，能力越强越好
- **A35B** = Active 35B（虽有 480B 总参数量，但只有 35B 被激活，即剪枝后的高效模型）
- **Think** = 推理模型，回答前先用 think 标记输出思考过程

## 数据准备

### 数据获取方式

1. **甲方提供** — 做项目时甲方有义务提供数据
2. **生产数据** — 如 HTTP 日志等生产过程中产生的数据
3. **网络抓取** — 有风险，需注意合规
4. **公开数据集** — Hugging Face、Kaggle、ModelScope、AWS 等
5. **合成数据** — 通过大模型从种子数据扩增

### 数据清洗

- **脱敏**：去掉身份证号、姓名等隐私信息
- **去标签**：去掉 HTML 标签、特殊字符
- **去广告**：去掉无关广告内容
- **去重**：避免被动重复（训练时 epochs 已经主动控制重复次数）
- **拼写纠错**：修正拼写错误

### 质量控制

三种方式：

1. **人工抽样**：目测数据质量和对应关系
2. **统计分析**：用 pandas 统计词量分布、对话长度分布、词频等
   - 发现异常值（如回答长度为 0 或特别长）→ 写脚本过滤
   - 发现乱码高频出现 → 定位并剔除
3. **试调验证**：取 100 条试调，看学习率是否下降，回答是否达到预期

### 数据格式化

大模型需要特定格式的输入，常见格式：

1. **原始格式**（预训练用）— 纯文本，用于训练 base 模型
2. **指令格式**（单轮对话）— instruction + input + output
3. **对话格式**（多轮对话）— 带 history 上下文的对话
4. **反馈格式**（强化学习用）— 带得分（如 0.9、0.3）

常用格式：
- **ShareGPT 格式**：`conversations` 数组，每项有 `from` 和 `value`
- **Hugging Face 默认格式**：`messages` 数组，角色为 system/user/assistant

多轮对话格式最通用（即使只有一轮也可以用它，数组里只写一个元素即可）。

### 合成数据扩增

当数据量不足时（如只有 3 条），可用大模型扩增：
1. 选择高质量种子数据（必须非常代表意图）
2. 设计提示模板
3. 让更大的模型（如 70B+，通常 100B+）根据种子生成更多数据
4. 参数调节：temperature（随机度）、修改提示模板、改进种子数据
5. 生成后仍需重新清洗和质量控制

### 常见问题

- **微调需要多少数据？** 100 条就可以起步，1000 条效果更优。关键在于质量，质量足够好 60 条也可以。
- **微调不是预训练**，不需要全互联网数据规模的训练集。1000 条是概念参考级。
- **训练结果高度依赖数据质量**，数量不重要，质量第一。

## 训练框架

三个主流微调框架：

### 1. PyTorch Tune（Torch Tune）

- PyTorch 原生微调工具
- **特点**：命令行执行，无需写代码；内置多种微调配方
- **步骤**：下载模型 → 选择配方（全量微调/LoRA/分布式）→ 改配置文件 → 运行
- **缺点**：速度慢，简单数据也可能需要 8 小时
- 模型支持范围有限

### 2. Hugging Face Transformers（Trainer）

- 生态最大，啥都做
- 基于 Transformer 库
- 集成自己的生态和 API

### 3. Unsloth（本课程主要使用）

- 构建在 Hugging Face 框架之上，大量借用 Hugging Face API
- **特点**：
  - 训练速度非常快，显著优于 Torch Tune
  - 显存占用显著优化（可能只用其他框架一半显存）
  - LoRA 实现高效（手动推导并写死优化）
  - 支持模型丰富（906+ 个模型，DeepSeek、Gemma、Qwen、Phi、GLM 等都支持）
  - 内置多种量化方式（4bit、8bit、QAT 等）
- **安装注意事项**：
  - `pip install unsloth` 基本安装
  - 需根据 CUDA 版本和 PyTorch 版本安装对应版本
  - 需要安装 `cmake`（涉及 llama.cpp 编译）
  - 需要 `scc`（安全认证相关）
- **依赖**：底层依赖 PyTorch + Hugging Face 库

### 微调基本流程（通用三步）

1. **加载基座模型**
2. **准备数据集**（清洗、格式化）
3. **设置参数开始微调**

关键参数：
- **batch size**：一次喂多少条数据
- **epoch**：整个数据集跑一遍 = 1 epoch
- **learning rate**：学习率，通常线性递减
- **gradient accumulation**：小显存实现大 batch 的技巧
- **loss**：预测值与目标值的差距，逐步下降说明微调有效

### 量化

- 将参数从 8bit 压缩到 4bit 或 2bit
- 减少显存占用，让更大模型能在更小显存上运行

## 推理模型（Think/R1）的数据准备

如果要微调一个推理模型（会用 think 标签输出思考过程）：
- 数据不能只写最终答案，要把推理过程写出来
- 例如：计算 3² + 4²，不能只写 25，而要写"3的平方是9，4的平方是16，总和是25"
- 基座模型本身没有推理能力，需通过专门的强化学习来增加推理能力

## 避免多次微调

不建议把数据分成多份多次微调（如每天微调一次），因为每次微调都会修改参数，多次微调会覆盖之前的知识，导致遗忘。

**建议**：每次从基座模型重新开始，将所有数据集合并一次性完成微调。

## 模型部署

微调后的模型可保存为 safetensors 格式，然后通过**Ollama**等推理框架加载服务。
- 用户可以在 LM Studio 等本地工具中运行模型
- LM Studio 与 Hugging Face 连通，可下载和分享模型
- 推理框架自动适配模型所需的特定框架
