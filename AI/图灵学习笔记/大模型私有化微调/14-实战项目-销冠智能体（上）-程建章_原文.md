## 1. 项目总体架构

### 1.1 系统概览

今天我们讲一个销冠智能体的应用。这个项目是基于 LangGraph 架构的一个智能体项目。老师之前应该跟大家讲过 LangGraph 的一些基础知识了，我这里以实际项目带着大家一起把 LangGraph 的使用细节和实际操作过程过一遍。

**Agent 核心服务：**

| 模块 | 功能 | 说明 |
|------|------|------|
| **Chat Suggestion** | 聊天建议 | 根据聊天记录生成回复建议 |
| **Profile Suggestion** | 用户画像 | 根据客户信息生成用户画像 |
| **Schedule Suggestion** | 日程建议 | 聊天中提到时间约定时自动创建日程 |
| **Tag Suggestion** | 标签建议 | 根据客户信息帮助打标签 |
| **Customer Service** | 客服建议 | 客服回复过程中智能回复 |

数据来源：
- 员工与客户的聊天记录
- 客服会话记录
- 微信小店订单记录
- 客户标签信息

### 1.2 微信体系数据流

```
微信系统 (聊天/客服/订单事件)
    ↓ 事件通知
WeChat Notify (接收微信通知)
    ↓ 触发同步
WeChat Think (主动获取数据)
    ↓ 通过 Agent Client
LangGraph Store (持久化存储)
```

微信通知只告诉你有一个事件发生了，不会携带具体数据。需要主动去微信体系里面获取数据。不同的数据级别有不同的校验方法——有的是使用 token 和 access 加密，有的还有独立的加密库确保客户会话信息不被泄露。

LangGraph 中保存用户数据有两种方式：
1. **持久化** — 通过 LangGraph 的 `store` 保存长期数据
2. **临时** — 在单次请求过程中通过 `state` 在节点间传输临时数据

### 1.3 Agent 的两种运行模式

LangGraph 开发有两种模式，以数据库类比：

| 模式 | 类比 | 说明 |
|------|------|------|
| **嵌入式 (Embedded)** | SQLite（内嵌） | 作为组件加载到项目中，由你自己的程序控制 |
| **服务式 (Server)** | PostgreSQL（独立） | 独立于你的服务之外，通过 API 接口请求 |

本项目使用第二种方式——**LangGraph Server**。启动一个 LangGraph Server 作为独立运行的中间件服务器。

**服务式的好处**：
- 可以更独立地运营和维护 Agent
- 与应用程序解耦，升级改动只要兼容接口即可
- 适合以 Agent 为主体的业务场景

**服务式的限制**：
- 需要有 LangGraph 的 License（免费版有使用量限制）
- 生产环境需要 LangSmith Key（用于用量监控，不会获取数据）

> **取舍**：如果你的应用核心在业务逻辑里，Agent 只是其中一部分，嵌入式更灵活。如果你的业务主体就是 Agent，其他都是辅助，服务式更好。

## 3. LangGraph 数据存储结构

### 3.1 数据模型

LangGraph 的数据结构可以理解成一个**大的字典**，有三级结构：

```
Namespace (命名空间)
    └── Key (键)
        └── Value (值，字典类型)
```

### 3.2 员工信息

```python
# namespace = "employee"
# key = 员工ID
# value = {"id": 员工ID, "name": 员工姓名, ...}
```

### 3.3 外部客户信息

```python
# namespace = "external_user"
# key = 客户ID
# value = {"id": 客户ID, "union_id": 微信UnionID, ...}
```

**UnionID**：在整个微信体系里面，同一个微信用户在不同平台（公众号、小程序、企业微信、微信小店）有一个统一的 ID。前提是要统一注册腾讯的开发者平台并配置关联。

### 3.4 聊天消息结构

聊天消息使用 `from_to_sorted_key` 作为键，把两个人的对话按顺序拼接，确保不管是从谁发给谁，都能拿到完整的对话记录。

每条消息包含：
- `message_id` — 消息唯一 ID
- `from_to_sorted_key` — 对话拼接键
- `timestamp` — 格式化的时间戳
- `content` — 消息内容
- `sequence` — 微信体系的聊天编码（用于按天过滤）

### 3.5 数据存储位置

- **开发环境**：存储在 LangGraph 内部的字典（序列化到硬盘）
- **生产环境**：存储在 **PostgreSQL** 数据库中（通过 LangGraph 封装访问）

数据不直接存 SQL，而是通过 LangGraph 的 store API 操作，不需要自己写 SQL。

### 5.3 Assistant-Thread-Run 模型

LangGraph Server 的三个核心概念：

| 概念 | 说明 | 类比 |
|------|------|------|
| **Assistant** | 一个配置（configure） | 数据库实例 |
| **Thread** | 一次会话线程 | 数据库连接会话 |
| **Run** | 线程中的执行运行 | SQL 查询 |

系统设计：一个客户 + 一个员工 = 一个 Assistant。这样做的好处是数据不会相互打扰、不会泄露。

```python
# 创建 Assistant 的策略
assistant_id = f"{graph_id}_{user_id}_{external_id}"
```

这样约束了只能由内部员工服务对应的外部客户。

## 7. Human-in-the-Loop（人工在环）

### 7.1 为什么需要人工确认

在企业应用中，确定性是非常重要的。比如给客户打标签、修改用户画像——不能 AI 运行完了就直接写进去。需要有**人工确认**环节。

### 7.2 实现原理

LangGraph 原生提供了 `interrupt()` 方法实现中断：

```python
# 在节点中调用 interrupt，线程暂停在这里
interrupt_data = {
    "description": "已为客户生成新的Profile，请确认",
    "old_profile": state.old_profile,
    "new_profile": state.new_profile
}
interrupt(interrupt_data)
# 线程等待，直到收到 resume 才继续往下执行
```

**流程**：
```
generate (生成) → notify_feedback (通知确认) → [interrupt 等待]
    ↓ 用户确认 (resume)
update (更新写入) → end
    ↓ 用户放弃
end
    ↓ 用户要求重新生成
    返回 suggest 节点重新生成
```

### 7.3 节点跳转控制

节点的返回值通过 `Command` 控制：

```python
# 返回值约束了可以跳转到哪几个节点
return Command(
    go_to="profile_update",  # 或 "end" 或 "profile_suggest"
    update={"result": "confirmed"}
)
```

用 `Literal` 枚举约束可跳转的目标节点，避免字符串拼写错误。

### 7.4 企业微信通知

每一步操作都会通过企业微信应用消息通知员工：
- "已为客户生成新的Profile，需要您确认"
- "您选择了放弃更新"
- "更新成功"
- "更新失败（含异常信息）"

## 8. LangGraph 工程实践技巧

### 8.1 使用枚举管理字符串

Python 是解释型语言，字符串拼写错误要到运行时才能发现。**所有节点名、字段名用枚举管理**：

```python
from enum import Enum

class NodeName(str, Enum):
    WELCOME = "welcome"
    GENERATE = "generate"
    NOTIFY_FEEDBACK = "notify_feedback"
    UPDATE = "update"
```

### 8.2 State 定义规范

LangGraph 中数据流转基于 State。定义一个完整的 State 体系：

```python
class OverallState(TypedDict):
    # 全量 state
    messages: list
    user_info: dict
    ...

class InputState(TypedDict):
    # 输入 state（OverallState 的子集）
    user_id: str

class OutputState(TypedDict):
    # 输出 state（OverallState 的子集）
    result: dict
```

**最佳实践**：使用继承关系，`InputState` 和 `OutputState` 必须是 `OverallState` 的子集。中间的中间产物既不在输入也不在输出中体现。

### 8.3 结构化输出（核心）

大模型的结构化输出不是黑魔法——本质就是通过提示词告诉大模型想要的格式：

```python
def generate_profile(state):
    # 构建 prompt
    schema_definition = get_schema_json(ProfileModel)
    example = get_example_instance(ProfileModel)
    
    prompt = f"""
    你的任务是提取用户的Profile信息。
    
    数据结构定义（JSON Schema）：
    {schema_definition}
    
    示例：
    {example}
    
    要求：
    - 必须返回一个有效的 JSON 对象
    - JSON 前后不要有任何文本
    - 内容符合定义的结构
    
    用户数据：
    聊天记录：{state.chat_history}
    客服记录：{state.cs_history}
    订单记录：{state.order_history}
    现有标签：{state.tags}
    现有Profile：{state.profile}
    """
    
    result = llm.invoke(prompt)
    return validate_and_parse(result, ProfileModel)
```

关键要素：
1. **JSON Schema** — 告诉大模型数据结构的定义
2. **示例（Example）** — 让大模型更准确理解结构
3. **明确的约束描述** — "必须返回有效的 JSON，不要有任何前后文本"
4. **Pydantic 校验** — 用 `BaseModel` 校验输出类型

自定义 BaseModel 基类，自动生成 Schema 和 Example：

```python
class ProfileModel(BaseModel):
    items: list[ProfileItem]
    
    def get_schema_json(self):
        return self.model_json_schema()
    
    def get_example_instance(self):
        return ProfileModel(items=[...])
```

### 8.5 LangGraph Server 扩展能力

LangGraph Server 基于 **FastAPI** 构建，可以利用 FastAPI 的生态：

- **生命周期**：`startup` / `shutdown` 事件
- **中间件**：添加自定义 Header、请求日志
- **认证**：内置 Token/Password 认证机制

```python
# lifespan
async def lifespan(app):
    # 启动时
    await setup()
    yield
    # 关闭时
    await teardown()

# middleware
@app.middleware("http")
async def log_requests(request, call_next):
    print(f"Request: {request.url}")
    return await call_next
```

这些配置在 `langgraph.json` 中：

```json
{
    "web_app": "src/web/app.py",
    "auth": "src/auth/auth.py"
}
```

## 10. 扩展思考

**关于 RAG vs Agent**：Agent 不是替代 RAG，而是互补。把知识库整合进 Agent 系统，可以做更强大的应用。

**关于企业微信的定位**：企业微信是一个客户信息输入平台，但不是必须绑定的。核心能力可以剥离出来，接入飞书、钉钉甚至自己的 CRM 系统——只要能获取数据到 LangGraph 就行。

**关于 AI 工程化**：不管是叫 Prompt Engineering 还是 Context Engineering，本质都是把给大模型的指令工程化管理。理解了这个核心，就不会被各种新概念搞混。但模型本身的能力也很重要——参数太少、量化太狠的模型容易不听指令。
