# 量化（上）与 Soft Prompt 方法

## 一、微调路径：三种方式

微调大语言模型有三种主流路径：

### 1.1 无代码平台

- **魔搭（ModelScope）**：在线训练服务。选择一个基座模型，添加数据集（本地上传或在线选择），配置参数，无需写代码即可训练。
- **LLaMA Factory**：通过浏览器访问的外部 UI 界面，同样不需写代码。
- **OpenAI 微调 API**：针对闭源模型（GPT 系列）。上传数据集，通过 HTTP POST 创建一个微调任务（fine-tuning job），获得专属的自定义模型 ID。无需 GPU——运行在 OpenAI 云端。注意：微调后的模型价格更贵（约 $3/百万 token vs 基础模型约 $1.25/百万 token）。

### 1.2 基于框架的微调（本课程重点）

- 使用 `unsloth` 或 Hugging Face `PEFT` 等框架。
- **选择此路径的原因**：它是**中间档**——比无代码平台更具概念上的透明性，又比企业自研代码更模块化、更容易理解。
- **目标**：不仅仅是"学会微调"，而是要**理解背后的概念**（微调在做什么、涉及哪些模块）。打通这条路后，向上（无代码平台）或向下（企业自研代码）都会很轻松。

### 1.3 企业内部自研代码

- DeepSeek、Meta 等发布基座模型的公司，内部都有自己的微调代码，不会依赖 unsloth 等第三方框架。
- 代码追求**高内聚高耦合**以保证性能——例如 LoRA 可能直接在训练脚本中用十几行实现，而不是拆成独立模块。

## 二、Unsloth 安装排错

### 常见问题 1：安装后需重启

在 Jupyter notebook 环境中运行 unsloth，新安装的模块需要重启内核才能生效。在执行 `pip install unsloth` 后，点击 **Restart Kernel（重启内核）**。

### 常见问题 2：通过哈希值固定版本

如果最新版本有问题（概率很小但可能发生），可以安装旧的稳定版本：

```bash
pip uninstall unsloth
pip install unsloth@https://github.com/unslothai/unsloth/archive/<commit_hash>.tar.gz
```

查找 commit hash 的方法：
1. 打开 unsloth GitHub 仓库
2. 点击 **Releases**
3. 每个 release 都有一个对应的 commit hash（例如 `856cf94`）
4. 将该 hash 附加到 `@` 后面的 URL 中

`@` 参数实际对应 clone 时的 `--revision <commit_hash>` 参数。

## 三、Soft Prompt 方法

### 3.1 Hard Prompt vs Soft Prompt

| 维度 | Hard Prompt | Soft Prompt |
|------|-------------|-------------|
| 本质 | 人类手写的文字（中文/英文等） | 机器学习的 token 嵌入向量 |
| 搜索方式 | 人肉不断修改措辞 | 神经网络通过梯度下降自动搜索 |
| 可解释性 | 完全可解释 | 不可解释——反解回文字会得到胡言乱语 |
| 上限 | 受限于人类写提示词的能力 | 理论上与 hard prompt 的上限相同 |
| 存储 | 保存文本字符串 | 保存一小段 token ID 矩阵（几 KB） |

**Hard Prompt（提示词工程）**：传统方式——用自然语言写系统提示词。例如"你是一位专业的法律顾问……"或"你是一位心理咨询师……"。这就是**提示词工程**。

**Soft Prompt**：不再手写寻找最佳的提示词，而是把提示词的 token 留空作为**可训练的嵌入向量**。训练过程会自动找到最优的 token ID（不一定是人类可读的文字），使 loss 最小化。

> 核心洞察：对模型来说最佳的提示词，可能无法用任何人类语言表达——它可能是一个数字模式，比任何自然语言句子都能"更好地拟合曲线"。

### 3.2 Prompt Tuning（提示词微调）

- **做法**：在输入前面添加可训练的嵌入向量。这些嵌入向量从一个初始值开始（例如从"Classify this text"这样的种子文本初始化），通过反向传播优化。
- **调整的对象**：只调整输入嵌入层——不修改 Transformer 内部的权重。
- **类比**：像提示词工程，但"提示词"由模型自动学习，而非人类手写。
- **存储**：极其轻量——训练好的"提示词"仅需几个 token ID 的矩阵（通常 <1KB）。
- **持久化**：将学习到的嵌入矩阵保存到磁盘，推理时加载即可。

**示例架构**（情感/情绪分类）：

```
输入："I will definitely watch it again"
Hard prompt 方式：  输入 + "It is" + [MASK] → 模型预测 "great" → 查字典得知 "great" 为正面情绪
Soft prompt 方式：  输入 + [T1][T2][T3]（可训练 token）→ 模型预测 → 计算 loss → 更新 [T1][T2][T3]
```

### 3.3 P-Tuning

- **对 Prompt Tuning 的扩展**：不仅可以在开头插入 token，P-Tuning 可以**在输入的任何位置插入可训练 token**（前面、中间、后面均可）。
- **生成机制**：使用 LSTM 或 Transformer 来生成提示词嵌入（而不是简单的可训练查找表），训练信号更复杂。
- Prompt Tuning 和 P-Tuning 都属于 **soft prompt** 家族。

### 3.4 Prefix Tuning（前缀微调）

- **进一步扩展**：除了调整输入嵌入层（Prompt Tuning），Prefix Tuning 还**在所有 Transformer 层的 KV cache 中添加可训练参数**。
- **KV Cache 回顾**：在自回归生成过程中，每个 token 的 Key 和 Value 向量会被缓存，避免重复计算。Prefix Tuning 将可学习的前缀向量插入每一层的 KV cache 中。
- 这是一个自然的增量创新——调优更多的层以获得更好的效果。

### 3.5 Soft Prompt vs LoRA 对比

| 维度 | LoRA | Soft Prompt |
|------|------|-------------|
| 调什么 | Transformer 内部权重（通过低秩矩阵） | 输入嵌入层 / KV cache 前缀 |
| 参数量 | 取决于秩，可能较大 | 非常小（几 KB 到几十 KB） |
| 需要降秩否 | 需要降秩（因为基座模型信息量饱满） | 不需要——参数量太少无需降秩 |
| 模型变更 | 产生新的模型变体 | 不改变基座模型本身 |
| 能力上限 | 无上限（可以学习新能力） | 受限于提示词工程的天花板 |
| 使用场景 | 需要深度任务适配时 | 成本敏感场景，大量用户各自需轻度定制 |

**什么时候用 Soft Prompt**：

- 大量用户各自需要轻度定制（例如 API 服务中每个用户获得一个"个性化模型"——实际上只是一个几 KB 的学习前缀）
- 成本敏感环境：存储 1000 个用户适配只需几 MB，而非 1000 个独立的 LoRA 适配器

**类比**：想想角色扮演 AI /"酒馆"(Tavern)服务——每个角色由一段提示词定义。Soft Prompt 让每个角色的"激活"变成一个学习的嵌入向量，而不是手写的文本块，效果可能更好且体积极小。

## 四、量化基础

### 4.1 为什么量化？

**目标**：让模型**变小** → 推理更快，显存需求更低。

- 量化缩小模型体积；微调（LoRA）则不会缩小模型，反而会添加适配器
- 模型越小，计算自然越快，能在更便宜的硬件上运行

**示例——DeepSeek R1（671B）**：
- 原始（FP16）：约 404 GB 显存
- 1.58-bit 量化后：约 140 GB 显存
- 虽然消费级显卡仍无法运行，但企业托管成本大幅降低

> 关于"1.58-bit"的解释：并非所有层使用相同的比特宽度——有的用 1-bit，有的用 2-bit，有的用 4-bit，各矩阵平均后得到 1.58 这样的小数。

### 4.2 什么是量化？

**定义**：将**连续值**转换为**离散值**。

想象模数转换的过程：
1. **采样**：在离散的时间点上取值（例如每秒一次）
2. **量化**：在每个采样点，将连续值四舍五入到最近的离散等级

在模型权重的语境下：
- 原始权重是浮点数（连续、高精度）
- 量化后的权重被舍入到一组有限的离散值（例如 4-bit 只有 16 种可能的值）
- **权衡**：模型变小但精度降低（信息损失不可避免）

### 4.3 量化对模型性能的影响

- 量化**确实会导致精度损失**——原始值与舍入值之间的差值就是丢失的信息
- 但量化带来的性能下降通常**小于**直接缩小模型架构（减少参数量）带来的损失
- 通常更倾向于保留大模型但做量化，而不是从头训练一个更小的模型

### 4.4 显存需求计算

**总显存需求 = 基座模型显存 + 微调权重 + 中间值 + 框架开销**

#### 4.4.1 基座模型显存

```
基座模型显存 = 参数量 × 每参数字节数
```

| 精度 | 每参数字节数 | 示例：8B 模型 |
|------|-------------|--------------|
| FP32 | 4 字节 | 32 GB |
| FP16 / BF16 | 2 字节 | 16 GB |
| INT8 | 1 字节 | 8 GB |
| INT4 | 0.5 字节 | 4 GB |

- "8B" 表示 80 亿参数
- 1 GB ≈ 10 亿字节（此近似计算中）
- 所以 8B 模型在 FP16 下需要约 8B × 2 = 16 GB 显存

#### 4.4.2 微调权重（LoRA）

- 取决于秩（r），通常非常小
- 典型配置下约 0.1–0.2 GB

#### 4.4.3 中间值

```
中间值 ≈ 批大小 × 上下文长度 × （某缩放因子）
```

- 经验值：batch size = 1，context = 8K 时，中间值约 4 GB
- 大致与批大小和上下文长度呈线性关系

#### 4.4.4 框架开销

- unsloth 框架开销：约 0.3–0.4 GB（保险估算约 1 GB）

#### 4.4.5 计算示例

使用以下配置微调 **LLaMA 3 8B**：
- 精度：FP16
- 批大小：1
- 上下文长度：8K
- 框架：unsloth

| 组件 | 显存 |
|------|------|
| 基座模型（8B × 2 字节） | 16 GB |
| LoRA 权重 | ~0.1 GB |
| 中间值 | ~4 GB |
| 框架开销 | ~1 GB |
| **总计** | **~21 GB** |

> 如果**只推理不微调**：去掉 LoRA 权重（~0.1 GB），batch size 降为 1，中间值降为 ~0.5 GB。总计减少约 4 GB。

### 4.5 在线显存计算器

[大语言模型显存与性能计算器](https://llm-vram-calculator.com/)（课件中也可找到）。支持选择：
- 模型（例如 DeepSeek 671B）
- 精度（量化级别）
- LoRA 秩
- 批大小
- GPU 类型

### 4.6 Unsloth 中的量化——`load_in_4bit` 参数

- 在 unsloth 框架中，设置 `load_in_4bit=True` 开启量化
- 这就是 **Q-LoRA 中的 Q**（上一节课未讲的 LoRA 变体）
- 示例：LoRA 在 FP16 下 → 模型约 29 GB（磁盘）；Q-LoRA 在 4-bit 下 → 模型约 7.5 GB（磁盘）
- 比值大致匹配比特宽度比：16 / 4 = 4，而 29 / 7.5 ≈ 3.9

## 五、代码实践——用 Hugging Face PEFT 做 Prompt Tuning

### 5.1 任务：Twitter 投诉分类

- **目标**：给定一条推文，判断它是否属于**投诉（complaint）**
- **数据集**：Twitter 投诉数据集（已标注）
- **框架**：Hugging Face `PEFT`（因为 unsloth 不支持 soft prompt 方法）
- **注意**：unsloth 专注于 LoRA；Prompt Tuning 能做的事，LoRA 也都能做（如果你不在乎额外成本的话）

### 5.2 关键步骤

1. **初始化配置**：
   - 从 Hugging Face Hub 加载模型（一个序列分类基座模型）
   - 设置 `PromptTuningInit`，使用种子文本（例如 "Classify this text"）
   - `prompt_tuning_init_text`：用于引导学习提示词的初始文本

2. **加载和处理数据集**：
   - 使用 Hugging Face `load_dataset`（与 unsloth 的 `load_dataset` 模式相同）
   - 转换为模型可兼容的格式（分词后的输入 → 标签）

3. **设置训练器**：
   - 从模型名称加载基座模型
   - 将 PEFT 模型包装在基座模型之上
   - 优化器：默认 AdamW
   - 训练循环：手写（不像 unsloth 那样一行 `.train()` 搞定）

4. **训练**：
   ```python
   for epoch in range(num_epochs):
       for batch in dataloader:
           loss = model(batch)
           loss.backward()
           optimizer.step()
   ```
   - 在典型的云 GPU（如腾讯云）上训练约需 50 分钟

5. **保存和加载**：
   ```python
   model.save_pretrained("./workspace/model")
   ```
   - 保存后的适配器非常小（实际训练的 prompt 仅 ~33 KB；加上分词器文件约 21 MB）
   - 重新加载：先加载基座模型，再加载 PEFT prompt 层

6. **推理示例**：
   - 输入："I have no water, and bill is currently paid. Could you do something about this?"
   - 模型输出：`label = complain`（正确识别为投诉）

### 5.3 核心要点

微调中真正有价值的是**你的数据集**，而不是代码——代码都是模板化的（几百行而已）。即使是开源模型的发布，价值主要也在训练好的权重，而不是训练脚本。

## 总结

| 主题 | 关键点 |
|------|--------|
| 微调三种路径 | 无代码平台 / 基于框架（课程重点）/ 企业自研。本课程选中间路径以理解概念。 |
| Soft Prompt | 可训练的嵌入向量替代人写提示词。比 LoRA 轻量，但受限于提示词工程的天花板。 |
| Prompt Tuning | 在输入嵌入层前添加可训练 token。 |
| P-Tuning | 可在任何位置插入 token；用 LSTM/Transformer 生成提示词嵌入。 |
| Prefix Tuning | 在所有层的 KV cache 中添加可训练参数。 |
| 量化 | 连续值 → 离散值。模型变小变快，代价是精度损失。 |
| 显存公式 | 基座模型（参数 × 字节数）+ LoRA 权重 + 中间值 + 框架开销。 |
| 代码实践 | 用 Hugging Face PEFT 对 Twitter 投诉分类做 Prompt Tuning。 |
