## 二、产品定义

### 2.1 我们要做什么

构建一个**基于微调大模型的视频转码监控与告警平台**，核心能力：

- **输入**：视频转码过程中各个组件产生的日志
- **输出**：日志分类（成功/失败）+ 根因分析 + 解决方案建议 + 自动告警

### 2.2 为什么需要这个系统

视频转码平台面临三大运维难题：

1. **日志来源复杂，格式混乱**
   - 转码流程涉及多个组件：视频下载（云平台工具）、截图（开源工具）、转码（FFmpeg）、杜比音效（商业SDK）、HDR处理、P2P分发、CDN上传等
   - 每个组件的日志格式各不相同，且不受运维团队控制
   - 日志不是结构化的行记录，而是一大段连续文本，错误信息隐藏在其中

2. **系统链路长，故障发现滞后**
   - 一个视频从上传到分发，可能需要6-7小时
   - 中间某个环节出错，往往要到用户端看到花屏/卡顿才被发现
   - 定位问题需要回溯整个链条，耗时极长

3. **故障处理SOP难以收敛**
   - 传统日志系统（如ELK/Zabbix）能完美处理HTTP日志，是因为HTTP的格式和状态码含义是固定的
   - 但转码平台的各组件频繁更新（杜比、DRM、云平台工具都在变），故障模式不断变化
   - 运维人员的经验难以文档化和扩散

### 2.3 大模型方案的优势

- 能够处理非结构化、不断变化的日志文本
- 通过微调可以学习特定组件（如杜比、FFmpeg）的私有错误模式
- 可以7x24小时不间断读取所有日志，人力无法做到
- 能够归纳总结、识别隐含的故障信号

## 三、需求拆解

整个项目分为三个核心步骤：

```
数据采集（转码日志） → 微调模型（分类+根因分析） → 构建告警服务
```

### 3.1 技术目标

1. **领域专家**：模型对视频转码领域的日志特别熟悉，能识别各类组件的错误模式
2. **可执行**：模型不仅能分析问题，还能调用外部API（重启任务、回滚版本、扩容等）
3. **集成预警**：实时分析日志，发现问题立即告警，避免故障传递到用户端

### 3.2 系统架构

```
                    ┌─────────────────────┐
                    │   视频转码原有系统    │
                    │  (下载→截图→转码→分发)│
                    └────────┬────────────┘
                             │ 读取日志（非侵入式）
                             ▼
                    ┌─────────────────────┐
                    │  微调后的LLM模型      │
                    │  (转码知识库微调)      │
                    └────────┬────────────┘
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
          ┌──────────────┐    ┌──────────────────┐
          │  告警系统API   │    │  故障自动处理API   │
          │ (发短信/微信告警)│    │ (重启/回滚/拉新镜像)│
          └──────────────┘    └──────────────────┘
```

关键设计原则：**非侵入式**——模型只读日志，不影响原有生产流程。即使模型宕机，原有转码业务照常运行。

## 四、视频转码平台背景介绍

### 4.1 输入输出模型

**输入多样性**（十几种来源）：

| 输入类型 | 来源 |
|---------|------|
| MP4 | UP主/创作者上传 |
| TS | 直播流 |
| 视频母带 | 影视剧制作方 |
| 蓝光光盘 | 采购的海外版权 |
| 卫星信号 | NBA等直播赛事 |
| 4G背包回传 | 新闻采编现场 |

**输出多样性**（格式 × 码率 × DRM × 后处理）：

同一视频需要根据以下维度准备多个版本：
- **设备类型**：手机（Android/iOS）、网页、电视
- **清晰度**：低清、标清、高清、超清、4K
- **音效技术**：普通、珍奇音画、HDR、杜比音效
- **网络条件**：4G低码率、WiFi高码率

一个好莱坞大片可能产生 **40 多种不同的码流**。

### 4.2 技术架构

```
内容生产者 → 视频平台 → 转码服务(Media Transform Service)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
              元数据提取             截图/预览图
              视频解码             抽帧/分段
              水印叠加             GOP转码
                    │                   │
                    └─────────┬─────────┘
                              ▼
                     CDN分发 → 用户观看
```

**运营后台**：运营人员可在后台配置转码策略（优先级、水印、清晰度分配等）。

### 4.3 内部处理流程

1. **下载视频**：从云平台内部存储拉取原始视频
2. **下载水印**：根据运营配置动态获取水印图像
3. **预处理**：截图封面、生成预览图、抽帧
4. **分离音视频**：音频单独处理
5. **分段**：视频切成10秒一段（GOP单位）
6. **转码**：每段转成目标分辨率（360p/1080p等）
7. **后处理**：叠加杜比音效、HDR等
8. **分发**：上传CDN

## 五、数据集准备

### 5.1 数据格式

原始数据来自数据库，字段包括：

| 字段 | 说明 |
|------|------|
| `successful` | 布尔值，是否成功 |
| `psnr` | 视频质量客观评分（浮点数） |
| `error_message` | 错误信息（成功时为空） |
| `solution_steps` | 解决方案步骤 |
| `tag` | 标签（如是否需要告警、可自动恢复等） |

示例：

```json
{
  "successful": false,
  "psnr": 0.0,
  "error_message": "编码器不支持 libx267",
  "solution_steps": "检查容器镜像，安装正确版本的编码器",
  "tag": "需人工介入"
}
```

### 5.2 数据清洗

清洗策略：

1. 先观察原始日志，发现典型错误模式
2. 将每种错误处理规则写入清洗脚本
3. 用脚本批量处理所有日志
4. 反复迭代：清洗 → 检查 → 补充规则 → 再清洗

> 数据清洗是枯燥但关键的一步。由于日志是机器产生的，同样的错误会批量出现，因此写脚本批量处理是最有效的方式。

### 5.3 格式转换：转为对话格式

最终训练数据采用 **ChatML 格式**：

```
{
  "conversations": [
    {
      "from": "user",
      "content": "<固定系统提示词>\n<日志内容>"
    },
    {
      "from": "assistant",
      "content": "<格式化的JSON回复>"
    }
  ]
}
```

**关键设计**：
- 统一系统提示词（不再使用原始数据中五花八门的提示词）
- 每条数据由"固定提示词 + 日志内容"组成
- 模型输出要求是**结构化JSON**（非自然语言），以便与API交互
- 输出字段固定：是否成功、PSNR质量分、错误信息、解决方案

### 5.4 提示词设计

统一使用一个固定的系统提示词，例如：

```
你是一个视频转码日志分析专家。请分析以下转码日志，按照固定JSON格式返回分析结果。
```

这样做的好处是：
- 微调时帮助模型明确输入边界
- 将模型输出固定在目标格式上
- 减少无关输出的干扰

## 六、模型微调流程

### 6.1 基座模型选择

选择策略：
1. 先选定几个候选模型（如 LLaMA、Qwen、Kimi 等）
2. 在微调前先用少量日志测试各模型的"先天理解能力"
3. 选择对视频转码领域**已有一定认知**的模型
   - 例如 LLaMA 本身就了解视频编解码概念（帧、时间戳、GOP等）
   - 选择"已经懂一点"的模型，微调效率更高

**选择结论**：选择**指令微调版本**的模型（而非基座模型），因为我们需要模型具备对话/指令跟随能力。数据量足够集中时，少量高质量数据也能达到良好效果。

### 6.2 使用 Unsloth 加载模型

```python
# 设置工作目录
import os
os.chdir("/workspace")

# 加载基座模型
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="your-base-model",
    max_seq_length=2048,
    dtype=None,          # 自动选择
    load_in_4bit=True,   # QLoRA 4bit量化
)
```

### 6.3 配置 LoRA

```python
model = FastLanguageModel.get_peft_model(
    model,
    r=16,                        # LoRA秩
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_alpha=16,               # LoRA缩放参数
    bias="none",                 # 不训练偏置
    use_gradient_checkpointing="unsloth",
    random_state=42,             # 随机种子
)
```

参数说明：
- `r=16` 是默认值，对少量数据效果较好
- Dropout：数据量不少时不需要，如果需要调参建议在 0.01-0.1 之间

### 6.4 加载本地数据集

```python
from datasets import load_dataset

dataset = load_dataset(
    "json",
    data_files="/path/to/your/data.json",
    split="train"
)
```

与从 Hugging Face 下载数据集不同，这里需要指定本地文件路径和 JSON 格式。

### 6.5 设置训练参数

```python
from trl import SFTTrainer

trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    dataset=dataset,
    dataset_text_field="text",
    args=transformers.TrainingArguments(
        per_device_train_batch_size=2,    # 单卡每次处理2条
        gradient_accumulation_steps=4,     # 梯度累积步数
        warmup_steps=5,                    # 学习率预热步数
        learning_rate=2e-4,                # 学习率
        logging_steps=1,                   # 日志打印频率
        optim="adamw_8bit",                # 优化器
        lr_scheduler_type="linear",        # 学习率调度策略
        output_dir="outputs",              # 输出目录
        num_train_epochs=1,                # 训练轮数
    ),
)
```

**关于学习率**：
- 学习率控制每次参数更新的步长
- 太大会导致震荡不收敛，太小则训练缓慢
- 理想策略：先大步探索，后小步精细调整（由优化器和调度器共同实现）
- warmup_steps 让学习率在前几步从小逐渐增大，避免初期大幅偏离

### 6.6 执行训练

```python
trainer.train()
```

训练过程观察：
- Loss 应该是**震荡下降**的趋势
- 不需要追求 Loss 降到 0，降到 0 意味着过拟合（模型把训练数据硬背下来了）
- 只要 Loss 在稳定下降，说明模型在向期望方向调整

### 6.7 保存模型

```python
model.save_pretrained("ffmpeg_log_analyze_model")
```

将微调后的 LoRA 权重保存到磁盘，下次可直接加载使用。

## 七、训练数据的最小化验证策略

在训练前，建议留出 2 条未参与训练的数据用于测试。训练完成后用这 2 条数据验证模型效果：

- 输入一条日志，看模型能否输出正确的 JSON 格式
- 检查字段是否完整、分类是否正确

如遇到训练错误，采用**问题最小化排查法**：
1. 回退框架版本（检查 unsloth 等是否有更新）
2. 换一个基座模型测试
3. 只用 1-2 条数据训练，缩小问题范围
4. 逐步锁定是模型问题、框架问题还是数据问题
