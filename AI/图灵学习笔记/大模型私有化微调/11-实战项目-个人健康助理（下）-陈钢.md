## 2. 模型评估（Evaluation）

### 2.1 评估的两个阶段

| 阶段 | 目标 | 主要手段 |
|------|------|---------|
| **上线前** | 对齐需求、说服组织达到上线标准 | 机器评估框架（自动化）、竞品对比 |
| **上线后** | 收集 Bad Case，持续改进 | 日志分析、用户反馈（点踩/转人工/重复提问） |

**上线前评估的核心作用：**
1. **对齐需求** — 让产品经理写测试集和标准答案，微调结果匹配其预期即满意
2. **说服组织** — 设定竞品标杆（如调用竞品 API 跑出分数），达到或接近即可上线
3. **说服自己** — 知道何时停止调优；完美不可达，需要客观指标决定上线时机

**上线后评估的重点：**
1. **Bad Case 采集**：重复提问（简单去重即可识别）、点踩内容、转人工前的对话
2. **回归测试**：每次改进后，用评估框架自动重跑测试集，确保之前的好结果未被破坏
3. **数据集管理**：多次微调的数据集尽量合并为一次训练，避免分多次微调导致的遗忘

> 费曼说：上线前用机器评估框架打分，知道什么时候能上线；上线后盯着 Bad Case 和回归测试，确保越改越好而不是越改越差。

### 2.2 机器评估的三类方式

| 类型 | 方法 | 适用场景 | 优点 | 缺点 |
|------|------|---------|------|------|
| **客观题** | 选择题（ABCD），模型预测与标准答案比对打分 | 有明确正确答案的测试 | 简单、精确、可自动化 | 不适合开放式问答 |
| **大模型法官** | 用更高参数的大模型（如千问 Max）评估结果 | 需要语义理解的评估 | 灵活、理解上下文 | 成本高、数据需暴露给第三方 |
| **文本匹配算法** | BLEU / ROUGE | **开放式问答**（无标准模板答案） | 无需人工、无需第三方模型 | 未考虑语序和语义 |

> 本次项目恰好属于第三种——医疗报告分析是开放式问答，没有固定格式的标准答案，又不能将数据交给第三方大模型评估。

### 2.3 BLEU 算法

**全称**：Bilingual Evaluation Understudy（双语替身评估）

**核心思路**：计算模型预测结果与标准答案之间的 n-gram 匹配精确度。

**基本版（朴素精确度）的问题：**
- 将预测结果逐词与标准答案比较，只要命中就得分
- **漏洞**：预测结果全部由标准答案中的词组成，但不构成合理语句，仍可能得满分

**改进版（BLEU）**：
- 限制每个词在标准答案中的命中次数，最多得 `1/N` 分（N 为标准答案总词数）
- 例：标准答案 "我提笔只为筹"，预测结果 "我我我我" → 命中 4 个"我"，每个权重 `1/7`，得分 `0.1428`（14 分）

**BLEU-N 中的 N 含义**：

| 版本 | 分词粒度 | 说明 |
|------|---------|------|
| BLEU-1 | 一元分词（unigram） | 每个字/词独立匹配 |
| BLEU-2 | 二元分词（bigram） | "我提"、"提笔"、"笔只"、"只为"、"为筹" 分别匹配 |
| BLEU-3 | 三元分词（trigram） | 三个连续词为一组匹配 |
| BLEU-4 | 四元分词（4-gram） | 四个连续词为一组匹配 |

- N 越大，要求越严格；BLEU-∞ 等价于要求精确相等
- **多人均看重更高 N 的分数**，因为它更体现语句的整体准确性
- BLEU **仅考虑精确度（Precision）**，未考虑召回率（Recall）

**BLEU 的弊端**：
- 未考虑语序
- 存在作弊空间：模型通过生成冗长回答，尽可能覆盖标准答案中的词，可刷高分数

### 2.4 ROUGE 算法

**全称**：Recall-Oriented Understudy for Gisting Evaluation

**与 BLEU 的核心区别**：
- BLEU 只看**精确度**（预测结果中有多少词在标准答案里）
- ROUGE 同时考虑**精确度 + 召回率**，并融合为一个综合分数

**召回率的意义**：标准答案中有多少词被模型成功预测出来了

```
例：标准答案 = "龟功嫌车不够 80 道好车怕人偷"
    预测结果 = "龟功嫌车不够"（只有前半句）
    → BLEU 得分：1.0（全部命中，满分）
    → ROUGE 得分：0.5（命中一半，召回率 0.5）
```

> 费曼说：BLEU 看"我说的话里有多少在标准答案里"（精确度），ROUGE 还看"标准答案里有多少被我正确说出来了"（召回率）。两者结合使用，互相补充。

### 2.5 评估框架选择

| 框架 | 开发者 | 老师评价 |
|------|--------|---------|
| **EvalScope** ⭐ | 阿里 | 推荐使用——精度高、使用体验好、兼顾中英文 |
| OpenCompass | 社区 | **强烈不推荐**——硬 bug 多，每个模型都有问题，浪费了大量时间 |

**OpenCompass 的替代方案**：
1. 将其内置测试集**直接拿出来**，转成 EvalScope 格式使用
2. 通过 EvalScope 的子库调用 OpenCompass 后端

> 注意：对框架的评价有时效性（约一个月），建议使用前重新评估。

## 3. EvalScope 评估实战

### 3.1 环境准备

```
Python 版本要求：3.10（官方建议）
安装方式：创建专用虚拟环境 → pip install 依赖 → 安装 EvalScope
```

**安装步骤：**
```bash
conda create -n evalscope python=3.10
conda activate evalscope
pip install torch==<对应版本>  # 根据 CUDA 版本选择
pip install evalscope
```

> 若直接安装报错，看缺少什么依赖就补装什么，是可行的。

### 3.2 数据集准备

本次使用 **CNB 医疗问答数据集**（Chinese Medical Benchmark 的子集），特点：
- 基于问答（QA）格式，适合开放式评估
- 数据量较小，适合作为测试集而非训练集
- 原始格式为问答对，需转换为 EvalScope 接受的格式

**本地数据集格式（JSONL）**：
```jsonl
{"query": "医生你看我这个检查报告...", "answer": "您的指标中...", "response": ""}
{"query": "...", "answer": "...", "response": ""}
```

- JSONL = JSON Lines，每行一个完整的 JSON 对象
- `query`：用户问题；`answer`：标准答案；`response`：（待模型填充）

### 3.3 评估脚本编写

```python
# eval_before_tuning.py — 评估基座模型
import evalscope

# 配置参数
dataset_config = {
    "dataset": {
        "format": "general_qa",      # 问答格式
        "local": "QA",               # 本地目录名
        "files": ["my_data.jsonl"],  # 数据集文件名
        "subsets": ["default"]       # 子集名
    }
}

model_config = {
    "model": "Qwen2.5-7B",  # 基座模型名（自动从 ModelScope 下载）
    "device": "cuda"
}

# 运行评估（耗时约 1-2 小时）
evalscope.run(model_config, dataset_config)
```

```python
# eval_after_tuning.py — 评估微调后的模型
dataset_config = {
    "dataset": {
        "format": "general_qa",
        "local": "QA",
        "files": ["my_data.jsonl"],
        "subsets": ["default"]
    }
}

model_config = {
    "model": "./output/qwen2.5-7b-lora-bnb-4bit",  # 本地微调后的模型目录
    "device": "cuda"

```

**为什么要写两个脚本？**
1. 回归测试需要——每次改进后重跑，对比分数变化
2. 追踪基座模型——持续监控基座模型的新版本得分，避免被反超而不自知

### 3.4 评估结果解读

**评估输出结构：**
```
outputs/
└── 2025-09-06_23-45-00/    # 每次评估以时间戳命名
    ├── report/
    │   ├── bleu-1: 0.07
    │   ├── bleu-2: 0.02
    │   ├── bleu-3: 0.0076
    │   └── bleu-4: 0.003
    ├── predictions/         # 模型预测的详细结果
    └── logs/                # 运行日志
```

**微调前后对比示例：**

| 指标 | 基座模型（Before） | 微调后（After） | 结论 |
|------|------------------|----------------|------|
| BLEU-1 | 0.16 | 0.12 | 微调后略下降 |
| BLEU-2 | 0.26 | **0.35** | **微调后显著提升** |
| BLEU-3 | 0.16 | 0.154 | 基本持平 |
| BLEU-4 | 0.06 | 0.03 | 微调后略下降 |

**结果分析**：
- 互有胜负，不是全面超越——主要优化目标是让回答更简洁（缩短输出长度）
- BLEU-1 下降是预期行为（回答变短后命中率降低），但 BLEU-2 提升说明二元词组匹配更好
- **本项目的上线标准**：在医疗领域内超过基座模型表现即可上线

> 费曼说：微调不是万能的，不是每次微调后所有指标都提升。关键是设好你的上线标准——在此项目中"比不调好"就是及格线。同时用回归测试确保没把原来好的地方改坏。

## 4. Flask 后端医疗报告服务

### 4.1 为什么用 Flask

| 需求 | 用裸 Python 实现的难度 |
|------|----------------------|
| 文件上传（支持 Content-Length 和 Chunked 两种模式） | 约 150 行，需兼容两种上传模式 |
| 跨域处理（CORS） | 需手动处理 OPTIONS 预检请求 |
| 路由分发 | 需手动解析 URL 和方法 |
| **使用 Flask** | **几十行代码解决以上所有问题** |

**Flask 核心语法（装饰器路由）：**
```python
from flask import Flask, request, jsonify

app = Flask(__name__)

# 基本路由
@app.route("/")
def hello():
    return "Hello World"

# GET 请求 + 参数
@app.route("/llm", methods=["GET"])
def llm():
    return "Hello, I'm Qwen2.5"

# 路径参数
@app.route("/user/<username>", methods=["GET"])
def user(username):
    return f"This is {username}"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=80, debug=True)
```

### 4.2 医疗报告服务架构

```
用户浏览器 ──→ [Flask 医疗报告服务 :80]
                        │
            ┌───────────┴───────────┐
            ↓                       ↓
    [多模态 VLLM :8000]      [语言 VLLM :8001]
    (分析报告图片)           (生成健康建议)
            ↓                       ↓
      analyze_result        health_recommendations
            └───────────┬───────────┘
                        ↓
              返回 JSON 给前端
```

**架构决策**：将 Flask 服务直接部署在有多模态 VLLM 的机器上
- 图片上传到 Flask 后，传给多模态模型是**本地传输**（127.0.0.1），速度极快
- 若不这样部署，用户图片需经 "用户 → Flask → 多模态" 两次网络传输，延迟翻倍

### 4.3 核心代码解析

```python
from flask import Flask, request, jsonify
from flask_cors import CORS
import base64
from PIL import Image
import io

app = Flask(__name__)
CORS(app)  # 跨域支持

@app.route("/analyze_medical_report", methods=["POST"])
def analyze_medical_report():
    print("收到医疗报告分析请求")
    
    # Flask 一行解决文件上传
    file = request.files["image"]
    image = Image.open(io.BytesIO(file.read()))
    
    # 防守性缩放（防止超大图片）
    max_size = 1280
    if max(image.size) > max_size:
        image.thumbnail((max_size, max_size))
    
    # 编码为 base64 传给多模态模型
    img_base64 = encode_image_to_base64(image)
    
    # Step 1: 多模态模型分析报告图片
    analyze_result = analyze_image(img_base64)
    print("图像分析完成")
    
    # Step 2: 将分析结果传给语言模型获取健康建议
    health_recommendations = get_health_recommendations(analyze_result)
    print("健康建议生成完成")
    
    # 合并结果返回
    return jsonify({
        "analyze_result": analyze_result,
        "health_recommendations": health_recommendations
    }), 200

def analyze_image(img_base64):
    """调用多模态 VLLM 分析医疗报告图片"""
    response = requests.post(
        "http://127.0.0.1:8000/v1/chat/completions",
        json={
            "model": "qwen2.5-vl-7b",
            "messages": [{"role": "user", "content": [
                {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{img_base64}"}},
                {"type": "text", "text": "请分析这张医疗报告图片中的各项指标"}
            ]}]
        }
    )
    return response.json()["choices"][0]["message"]["content"]

def get_health_recommendations(analyze_result):
    """调用语言 VLLM 生成健康建议"""
    response = requests.post(
        "http://127.0.0.1:8001/v1/chat/completions",
        json={
            "model": "qwen2.5-7b",
            "messages": [{"role": "user", "content": f"根据以下指标分析给出健康建议：{analyze_result}"}]
        }
    )
    return response.json()["choices"][0]["message"]["content"]

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=80, debug=True)
```

**三个需配置的变量：**
1. `API_VL_MODEL` — 多模态模型名称（需与 VLLM 启动时的名称一致）
2. `API_LLM_MODEL` — 语言模型名称
3. `VLLM_IP` / `VL_IP` — 各自服务的 IP 地址（同机可用 127.0.0.1）

### 5.2 跨域问题（CORS）

**问题**：前端页面使用 HTTPS 域名（腾讯云临时域名），而 Flask 服务是 HTTP。浏览器默认会阻止"混合内容"（Mixed Content）。

**解决方案**：在浏览器中手动允许不安全内容
```
浏览器地址栏 → 点击锁图标 → 网站设置 → 不安全内容 → 改为"允许"
```

**服务端配置**（Flask 侧）：
```python
from flask_cors import CORS
CORS(app)  # 允许所有跨域请求
```

### 5.3 超时设置

由于上传图片和模型推理耗时较长，需要在前端设置较长的超时时间：

```javascript
// 前端 axios/fetch 超时设置
const timeout = 120000;  // 120 秒
// 实际流程：上传图片 ~50s → 多模态分析 → 语言模型推理
```

> 费曼说：Flask 用装饰器搞定路由和文件上传，比自己写 Python Socket 解析 HTTP 协议省了上百行代码。前端用纯 JS 无框架，启动简单，避免被前端工具的编译流程拖累。

## 6. 损管设计（故障隔离）

### 6.1 概念来源

**损管（Damage Control）** 源于海军术语——舰艇被击中后控制伤害不蔓延的能力。

- 二战美国企业号航母被击穿 6 次仍能修复并持续作战
- 日本航母损管差，一旦破洞进水就容易沉没

### 6.2 在软件中的体现

**两个前提：**
1. **团队能力** — 有训练有素的运维人员
2. **架构设计** — 系统本身要可运维、可隔离故障

### 6.3 本项目的损管设计

老师提供了**两个 Flask 脚本**：

| 脚本 | 推理后端 | 用途 |
|------|---------|------|
| `server_self_host.py` | 本地微调后的模型（VLLM） | 正常上线使用 |
| `server_openrouter.py` | OpenRouter 公共 API | **故障排查工具** |

**排查逻辑：**
1. 先用 `server_openrouter.py` 启动（使用稳定可靠的公共 API）
2. 如果能正常工作 → 前端 + Flask 没问题，问题出在自托管模型
3. 如果不能工作 → 问题出在前端或 Flask 服务本身
4. 通过二分法快速定位故障点

> 费曼说：做设计时就要想"出问题了怎么排查"。提供一个稳定的备用路径帮你快速二分定位问题，这个思路比你查半天代码高效得多。

## 7. VLLM 部署与监控

### 7.1 VLLM 启动配置

```bash
# 多模态模型（端口 8000）
vllm serve qwen2.5-vl-7b --port 8000 --max-model-len 1024

# 语言模型（端口 8001）

```

### 7.2 监控方案（Prometheus + Grafana）

VLLM 官方推荐使用 **Prometheus**（数据存储）+ **Grafana**（可视化展示）监控推理服务：

| 监控指标 | 说明 |
|---------|------|
| 端到端请求时延（End-to-end latency） | 从请求发起到收到完整回复的总时间 |
| 每个 Token 的时延（Per-token latency） | 生成每个 Token 的平均时间 |
| 首 Token 时延（Time-to-first-token, TTFT） | 第一个 Token 输出的耗时（通常最慢） |
| Token 吞吐量（Token throughput） | 每秒生成的 Token 数 |

**安装 VLLM 常见问题与解决：**

| 问题 | 原因 | 解决 |
|------|------|------|
| pip install 安装失败 | CUDA / PyTorch 版本不兼容 | **方案一**：退回到兼容版本 |
| 预编译包版本不匹配 | 包为 torch 2.5.1 编的，但你用的是 torch 2.6.0 | **方案二**：从源码编译（`git clone` → 手动安装，约 40-50 分钟，兼容性最好） |
| unsloth 也类似 | 模型不断更新，推理框架和微调框架都需要跟进 | 优先用新版本，不得已时回退 |

### 7.3 并发与性能

- **实测并发数**：约 2（在 2060 显卡上使用 ab 压力测试得出）
- **提高并发的方法**：
  1. 增加显存（换更好的机器，新机器比旧机器快 4-5 倍）
  2. 减小模型规模（7B 能满足需求就不必用更大的）
  3. 减小上下文长度
  4. 纯代码加速（如 DeepSeek 的方法，与硬件结合可达 10 倍提升）

## 8. 工作流抽象（PocketFlow 源码分析）

### 8.1 什么是工作流（Workflow）

两个模型协同工作（多模态分析 + 语言模型建议）本质上就是一个工作流。

**成熟的 Workflow 框架需要解决的核心问题：**
1. **如何定义节点（Node）** — 每个节点封装一段逻辑
2. **如何让数据在节点间流转** — 串联执行

### 8.2 PocketFlow 设计思想

PocketFlow 是一个仅 100 行代码的极简工作流框架，适合用来理解工作流的本质抽象。

**源码核心：**

```python
class BaseNode:
    def __init__(self):
        self._next = None
    
    def __rshift__(self, other):
        """重载 >> 操作符，实现节点串联"""
        self._next = other
        return other
    
    def prepare(self):
        """准备阶段（可选）"""
        pass
    
    def execute(self):
        """执行阶段（必须实现）"""
        raise NotImplementedError

class Node(BaseNode):
    """普通节点"""
    def execute(self):
        # 执行节点逻辑
        pass
        return self._next

class BatchNode(BaseNode):
    """批量执行节点（循环）"""
    pass

class AsyncNode(BaseNode):
    """异步并行节点"""
    pass
```

**使用示例：**
```python
# 定义三个节点
class GenerateOutline(Node):
    def execute(self, data):
        data["outline"] = llm.generate_outline(data["topic"])
        return self._next

class WriteContent(Node):
    def execute(self, data):
        data["content"] = llm.write_content(data["outline"])
        return self._next

class ApplyStyle(Node):
    def execute(self, data):
        data["result"] = llm.apply_style(data["content"])
        return self._next

# 串联成工作流
flow = GenerateOutline() >> WriteContent() >> ApplyStyle()
flow.run({"topic": "大模型微调"})
```

### 8.3 从工作流抽象中得到的启示

**工作流的核心抽象 = Node（节点）+ Flow（流转）**

| 维度 | 说明 |
|------|------|
| **串联** | 节点依次执行，前一节点的输出是后一节点的输入 |
| **并联** | 异步节点可并行执行，提升吞吐 |
| **批量** | 批量节点循环处理多个输入 |
| **本项目的 Node 划分** | ① 接收图片 → ② 多模态分析 → ③ 语言模型生成建议 |

> 费曼说：了解一个成熟框架的抽象不一定是为了用它，而是为了理解"这个概念到底是什么"。工作流就是"把逻辑拆成节点，用管道串起来"。你既可以用 PocketFlow/LangChain，也可以自己写几十行代码实现同样的模式。

### 9.2 核心要点

1. **微调三步走**：选基座模型 → 准备好数据集 → 选框架训练
