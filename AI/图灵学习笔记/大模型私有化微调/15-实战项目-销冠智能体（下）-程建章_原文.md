## 2. LangFuse 可观测性服务部署

### 2.1 为什么需要 LangFuse

LangSmith 本身兼顾了监控、Trace 和调试功能，但与 LangGraph 自身结合较紧密。**LangFuse** 的优势在于适配更广泛，能与很多服务做集成。

LangFuse 用 Docker 部署，非常简洁。依赖的组件：
- **PostgreSQL** — 数据库
- **Mini IO** — S3 存储
- **Redis** — 缓存
- **ClickHouse** — 大数据分析（经典服务）

### 2.2 部署步骤

```bash
# 第一步：克隆代码
git clone <langfuse-repo-url>

# 在国内访问 GitHub 有困难时，可使用代理
# https://github-proxy.com/ 将访问路径挂在下面即可
```

```bash
# 第二步：启动（进入项目目录）
docker compose up

# 后台运行
docker compose up -d
```

第一次启动时需要安装镜像，耗时较多。设置好 Docker 镜像加速可以加快速度。

### 2.3 访问与配置

启动后，服务运行在 **3000 端口**。通过端口映射访问：

```
Cursor 中配置端口映射：
  源：LangFuse 服务器的内网 IP:3000
  目标：本地端口（如 3000）
  中转：Agent 部署服务器（端口转发）
```

首次访问会进入注册页面，输入邮箱和密码即可注册。

**密码管理建议**：推荐使用密码管理工具：
- **1Password**（付费，跨平台）
- **iCloud 密码**（Windows 也可用）
- **LastPass** 等

### 2.4 创建项目与 API Key

注册后在 LangFuse 中创建项目 → 创建 API Key：
- 生成 **Public Key** 和 **Secret Key**
- 记下 **Host** 地址（LangFuse 服务器的内网 IP:3000）

## 3. LangFuse 功能演示

### 3.1 观察面板

面板核心指标：

| 指标 | 说明 |
|------|------|
| **Requests** | 请求次数统计 |
| **Cost** | 估算的大模型调用费用 |
| **Latency** | 延迟分析（99线/95线/50线） |
| **Tracing** | 每次请求的完整链路追踪 |

### 3.2 Trace 详细视图

每次请求的 Trace 可以清晰看到：

```
请求链路：
plan_up (清空) → welcome → load_employee → load_customer → load_tags → load_profile → generate → ...
```

每个节点都可以查看：
- **Input** — 节点收到的数据
- **Output** — 节点产出的数据
- **State** — 当前 State 内容
- **Duration** — 节点耗时
- **Token 消耗** — 输入/输出 Token 数

### 3.3 子图追踪

当执行到子图（Subgraph）时，Trace 会展开显示子图内部的节点执行情况，包括完整的提示词、历史记录等。所有变量用加粗显示，方便了解数据传输内容。

## 4. 代码集成 LangFuse

### 4.1 配置变更

只需修改三处地方：

**1. 环境变量配置（`.env`）**

```env
LANGFUSE_PUBLIC_KEY=your-public-key
LANGFUSE_SECRET_KEY=your-secret-key
LANGFUSE_HOST=http://your-langfuse-ip:3000
LANGFUSE_ENABLED=true
```

`LANGFUSE_ENABLED` 参数控制开关，无需改代码即可开启/关闭上报。

**2. 依赖添加（`requirements.txt`）**

```
langfuse==3.5.0
```

**3. State Graph 集成**

```python
# 加载环境变量
from langfuse import Langfuse
from langfuse.callback import LangfuseCallbackHandler

# 如果启用了 LangFuse
if langfuse_enabled:
    langfuse_handler = LangfuseCallbackHandler(
        public_key=public_key,
        secret_key=secret_key,
        host=host
    )
    
    # 在 compile 时加入 callback
    app = builder.compile(
        # ...原有参数
    )
    # 通过 with_config 注入 callback
    app.with_config({"callbacks": [langfuse_handler]})
```

### 4.2 代码变更总结

```
之前：只有 number_builder.compile(...)
之后：增加环境变量加载 + LangfuseHandler 创建 + with_config 配置
```

## 5. 生产环境数据库部署

### 5.1 为什么需要数据库

开发环境（`langgraph dev`）下，数据存储在 Python 内存对象中（序列化到缓存）。生产环境必须使用 **PostgreSQL** 和 **Redis**。

**服务资源估算**：2 核 4G 服务器，月费约几十元。

### 5.2 Redis 安装与配置

```bash
# 安装 Redis
dnf install redis -y

# 启动并设置开机自启
systemctl start redis
systemctl enable redis

# 测试
redis-cli
> set hello world
> get hello
"hello"
```

**安全配置**：

```bash
# 编辑配置文件 /etc/redis/redis.conf

# 设置密码
requirepass your_password

# 修改监听地址（从 127.0.0.1 改为 0.0.0.0 允许远程访问）
bind 0.0.0.0

# 重启 Redis
systemctl restart redis

# 带密码连接测试
redis-cli -a your_password
```

> **注意**：生产环境中建议创建只读账号，避免误操作。

### 5.3 PostgreSQL 安装与配置

```bash
# 安装 PostgreSQL 17（LangGraph 要求 >= 16）
dnf install postgresql17-server postgresql17-contrib -y

# 初始化数据库
/usr/pgsql-17/bin/postgresql-17-setup initdb

# 启动并设置开机自启
systemctl start postgresql-17
systemctl enable postgresql-17
```

**修改配置**：

```bash
# /var/lib/pgsql/17/data/postgresql.conf
port = 5432
listen_addresses = '*'
```

**认证配置**：

```bash
# /var/lib/pgsql/17/data/pg_hba.conf
# 允许远程 IP 访问
host    all    all    0.0.0.0/0    md5
```

**创建用户和数据库**：

```bash
# 以管理员身份进入
sudo -u postgres psql

# 创建用户
CREATE USER graph_user WITH PASSWORD 'your_password';

# 创建数据库
CREATE DATABASE langgraph_db OWNER graph_user;

# 测试连接（从远程）
psql -h <server_ip> -p 5432 -U graph_user -d langgraph_db
```

### 5.4 数据存储位置关系

| 环境 | 存储方式 | 说明 |
|------|---------|------|
| 开发 | In-memory（序列化到缓存） | 仅用于本地测试 |
| 生产 | PostgreSQL + Redis | Redis 管理运行时状态，PG 持久化数据 |

> **关于数据库是否用 Docker**：核心业务数据库不推荐放在 Docker 中，因为容易丢失数据。监控等非核心服务可以用 Docker。生产环境数据库一般有专门的运维同事管理，或使用云服务（阿里云 RDS 等）。

## 6. Docker 镜像构建与部署

### 6.1 Dockerfile 结构

```dockerfile
FROM python:3.12-slim

# 复制依赖文件
COPY requirements.txt /app/requirements.txt

# 设置环境变量（防止生成 pyc 文件）
ENV PYTHONDONTWRITEBYTECODE=1

# 安装依赖（使用 UV 加速）
RUN pip install uv && \
    uv pip install -r /app/requirements.txt

# 复制源代码
COPY src/ /app/src/

# 设置 LangGraph 配置
ENV LANGGRAPH_CONFIG=langgraph.json

# 暴露端口
EXPOSE 8000
```

### 6.2 构建镜像

```bash
# 构建并打标签
docker build -f Dockerfile -t agent-app:3.1 .

# 查看已有镜像
docker images

# 版本管理示例
# 3.0 — 基础版本
# 3.1 — 包含 LangFuse 功能
```

### 6.3 运行容器

```bash
# 前台运行（观察日志）
docker run --name agent-3.1 \
    --env-file .env \
    -p 9123:8000 \
    agent-app:3.1

# 后台运行
docker run -d --name agent-3.1 \
    --env-file .env \
    -p 9123:8000 \
    agent-app:3.1

# 查看日志
docker logs -f agent-3.1

# 停止/启动
docker stop agent-3.1
docker start agent-3.1
```

**端口说明**：
- **9123** → 生产环境端口（映射到容器内的 8000）
- **2024** → 开发环境端口（`langgraph dev` 默认）

### 6.4 验证部署

```bash
# 使用 Client SDK 测试
conda activate agent_env
python client/kind.py

# 查看数据是否正常
# 如果新部署没有数据，先执行数据初始化
python scripts/demo_init.py
```

## 7. 生产环境数据存储结构

### 7.1 Redis 运行时状态

Redis 主要负责管理运行时的状态：
- **Run** — 当前运行的线程
- 节点执行的 Checkpoint 状态

### 7.2 PostgreSQL 持久化表

| 表 | 用途 | 说明 |
|----|------|------|
| **assistant** | 助手配置表 | 存储创建的 Assistant 及其配置（Configure） |
| **thread** | 会话线程表 | 每个客户+员工组合对应一个 Thread |
| **checkpoint** | 节点执行记录 | 每个运行节点的状态快照 |
| **store** | 业务数据表 | Namespace/Key/Value 结构存储 |

### 7.3 Store 数据结构验证

通过 PostgreSQL 客户端可以看到：

```
namespace: "employee"          → 员工信息
namespace: "external_user"     → 客户信息
namespace: "setting_tag"       → 标签设置
namespace: "wechat_message"    → 微信消息（01号、02号...）
namespace: "wechat_cs"         → 客服消息
```

每条消息包含：
- `message_id` — 消息唯一 ID
- `from_to_sorted_key` — 对话拼接键
- `content` — 消息内容
- `from_id` — 发送者 ID

## 8. 企业微信 API 集成

### 8.1 常用接口分类

企业微信是中国触达客户最便捷的通道之一，特别是在 SCRM 场景中：

| 接口类型 | 说明 |
|---------|------|
| **内部成员** | 获取成员列表、管理标签 |
| **客户联系** | 获取客户列表、群管理 |
| **消息推送** | 接收和发送消息 |
| **客服** | 在微信客服通道中与用户交流 |

### 8.2 回调事件处理

企业微信使用消息通知（Callback）机制与服务器通信：

```python
# 回调接口 GET — 验证回调接口有效性
def callback_get(request):
    # 验证签名、时间戳、nonce
    # 解密 echo string 返回
    return echo_string

# 回调接口 POST — 接收消息通知
def callback_post(request):
    msg = decrypt(request.data)
    message_type = msg['MsgType']
    
    if message_type == 'text':
        return handle_message(msg)
    else:
        # 图片、声音、视频等，仅做简单回复
        return simple_reply(msg)
```

### 8.3 项目中使用的事件

项目中最常用的三个回调事件：

1. **Agent 需要用户确认时** — 发送通知给员工
2. **创建标签后** — 写入企业微信平台
3. **创建日程后** — 在企业微信中创建日程

回调消息结构示例：

```json
{
    "ToUserName": "企业ID",
    "FromUserName": "用户ID",
    "MsgType": "event",
    "Event": "kf_msg_or_event",
    "Token": "消息同步token"
}
```

> **注意**：不携带 token 也可以请求，但会有频率限制。拿着 token 请求消息同步接口时不会做限制。

## 9. AgentScope 框架介绍

### 9.1 框架概览

阿里最近开源的 **AgentScope** 框架，与 LangGraph 在理念上有很多相似之处，但结构更简洁清晰。

**核心特点**：
- 支持创建 ReAct Agent
- 提供内置 Tools（Python 执行、图片生成等）
- 支持多 Agent 交互（如多角色辩论）
- 提供 Runtime 库（类似 LangGraph 的嵌入式/服务式两种模式）
- 内置 Studio 可视化调试工具

### 9.2 创建 Agent 示例

```python
# 创建 ReAct Agent
agent = Agent(
    name="assistant",
    tools=[execute_python, ...]
)

# 调用
result = agent.run("创建一个运行 hello world 的命令")
```

AgentScope 支持多 Agent 协作，比如"多角色辩论"场景——多个 Agent 分别扮演不同角色，针对同一个问题展开讨论，逐步收敛到正确答案。

### 9.3 与 LangGraph 的对比

| 特性 | LangGraph | AgentScope |
|------|-----------|------------|
| 架构 | 图结构（节点+边） | 更加简洁的 API |
| 部署模式 | 嵌入式/服务式 | Runtime / 独立部署 |
| 可视化 | LangGraph Studio | AgentScope Studio |
| 多 Agent | 通过子图实现 | 原生支持 |
| 成熟度 | 快速发展中（1.0 即将发布） | 快速成长阶段 |

## 10. AI 工程化思考与总结

### 10.1 LangGraph 面临的挑战

- **版本不稳定**：接口在 1.0 发布前仍会变更，1.0 预计 10 月前发布
- **确定性问题**：传统编程是确定性输出（查 5 条就是 5 条），AI 时代变成了概率性输出
- **业务适配**：技术实现是一回事，把产品做好是另一回事，需要与业务运营共同优化

### 10.2 项目架构建议

模块划分的原则：
- **逻辑解耦**：降低复杂性，有利于项目稳步推进
- **团队协作**：拆开让团队成员更专注于各自模块
- **接口协议**：定义好接口协议，各部分可并行开发

> **经验之谈**：做过类似项目的人开发速度会快一倍以上。第一次使用 LangGraph 时需要花时间熟悉框架细节和 API。建议在预言性项目（POC）中先做实践，避免在生产项目中踩坑。

### 10.3 Agent vs Workflow 的思考

Agent 是不是 Agent 不重要，适用场景才重要：

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| 创造性任务 | ReAct 模式 | 由 AI 自主规划、使用工具 |
| 确定性流程 | Workflow 模式 | 对提效场景更有优势 |

### 10.4 一人公司与全栈能力

AI 时代的一个趋势是"一人公司"——利用 AI 工具，一个人可以完成过去一个团队的工作。建议：
- 学会使用 AI 编程工具（如 Cursor）
- 掌握从开发到部署的全栈能力
- 在小规模范围内能够独立交付可用系统
