# 实战项目下：视频转码日志报警平台（第2部分）

## 1. Unsloth 版本兼容问题

在课程期间，Unsloth 和其依赖的 Transformers 库发生了版本更新，导致两个问题：

1. **推理失败** — Transformers 库更新到了 4.56 大版本，其中存在不兼容的 breaking changes
2. **模型保存失败** — `save_pretrained_gguf` 方法在新版本中损坏

### 原因

Unsloth 的依赖配置文件 `pyproject.toml` 中声明了 `transformers >= 4.5.3`，没有设定上限版本，因此安装时会自动获取最新的 4.56 版本，而该版本存在兼容性问题。

该问题已在 Unsloth 官方 GitHub 上被确认。解决方法：
- **临时方案**：改用其他保存方法替代 `save_pretrained_gguf`
- **长期方案**：等待 Unsloth 后续版本修复，或手动固定 Transformers 版本

> **建议**：在项目依赖中明确指定版本号，而非仅使用 `>=`，避免被未来不兼容版本"坑到"。

## 2. vLLM 部署微调后的模型

### 2.1 安装 vLLM

```bash
# 创建虚拟环境（推荐使用 conda）
conda create -n vllm2 python=3.10 -y
conda activate vllm2

# 安装 vLLM
pip install vllm
```

> 安装大约需要 10 分钟。

### 2.2 查看虚拟环境列表

```bash
conda env list
```

### 2.3 启动 vLLM 服务

```bash
python -m vllm.entrypoints.openai.api_server \
    --model /path/to/your/fine-tuned-model \
    --host 0.0.0.0 \
    --port 80
```

**常见问题：显存不足（OOM）**

如果模型的上下文长度过大（如 128K），会导致显存溢出，报错信息如下：

```
模型的最长上下文为 128K，但显存不足以容纳
```

**解决方案**：限制模型上下文长度

```bash
python -m vllm.entrypoints.openai.api_server \
    --model /path/to/your/fine-tuned-model \
    --host 0.0.0.0 \
    --port 80 \
    --max-model-len 32768 \
    --gpu-memory-utilization 0.9 \
    --tensor-parallel-size 1 \
    --trust-remote-code
```

参数说明：
- `--max-model-len 32768`：限制最大上下文长度为 32K（单轮对话通常足够）
- `--gpu-memory-utilization 0.9`：GPU 显存利用率上限 90%
- `--tensor-parallel-size 1`：张量并行数（单卡设为 1）
- `--trust-remote-code`：信任远程自定义代码

成功启动后终端会显示：

```
Application startup complete. Waiting for application start.
Startup complete.
```

## 3. 测试已部署的模型

vLLM 提供了与 OpenAI API 兼容的接口，可通过 curl 调用。

### 3.1 安装 jq（可选，用于格式化 JSON 输出）

```bash
apt install jq
```

使用方式：

```bash
curl http://<your-ip>:<port>/v1/chat/completions -d '{...}' | jq
```

### 3.2 测试成功的转码日志

```bash
curl http://<your-ip>:80/v1/chat/completions \
  -d '{
    "model": "your-model-name",
    "messages": [
      {"role": "user", "content": "<转码成功的日志内容>"}
    ]
  }'
```

预期返回：`transcoding status: success`

### 3.3 测试失败的转码日志

```bash
curl http://<your-ip>:80/v1/chat/completions \
  -d '{
    "model": "your-model-name",
    "messages": [
      {"role": "user", "content": "<转码失败的日志内容>"}
    ]
  }'
```

预期返回：
- `transcoding status: failure`
- 包含 `error_message` 字段，描述错误原因
- 返回格式为 JSON（而非自然语言），说明模型微调成功

## 4. 告警平台完整架构

### 4.1 核心工作流程

1. **接收日志**：Python HTTP Server 接收来自视频转码服务器的日志
2. **调用大模型**：将日志发送给本地 vLLM 服务进行分析
3. **解析结果**：从大模型返回中提取以下字段
   - `success`：是否转码成功
   - `PSNR`：转码效果指标（Peak Signal-to-Noise Ratio）
   - `error_message`：失败时的错误信息
   - `solution`：AI 建议的解决步骤
4. **告警通知**：如果转码失败，通过飞书机器人发送告警消息到手机

### 4.2 Python Server 关键代码解析

```python
# main入口：启动一个HTTP服务
# 核心逻辑在 MyRequestHandler 中

# do_post 方法：
# 1. 接收POST请求中的日志内容
# 2. 构造发送给vLLM的消息体
# 3. 调用vLLM的API（与OpenAI API兼容）
# 4. 解析返回的JSON，提取关键字段
# 5. 根据结果决定是否发送告警

# prompt构造示例
data = {
    "model": "<模型目录名>",
    "messages": [
        {"role": "user", "content": "<提示词> + <日志内容>"}
    ],
    "format": "json",
    "stream": False  # 等待完整输出，而非流式返回
}
```

### 4.3 飞书机器人告警

当转码失败时，系统会调用 `send_feishu_notification` 方法发送告警消息到手机：

- **标题**：转码系统告警
- **内容**：转码异常 + error_message
- **AI 分析方案**：solution 建议
- **链接**：可点击跳转到内部系统

飞书机器人的配置步骤（手机端操作）：
1. 进入飞书群
2. 点击右上角"三个点"
3. 选择"群机器人"
4. 点击"添加机器人" → "自定义机器人" → "添加"

### 4.4 扩展性

- 可替代为企业微信接口或邮件通知
- 可在失败处理分支中添加自动重启转码任务等自动化操作
- 可通过 Python 前置层控制访问权限，防止他人滥用微调模型

## 5. 模型评估方法

### 5.1 人工评测（Manual Evaluation）

- **适用场景**：所有任务，尤其没有标准测试集的新领域
- **优点**：最准确，无领域限制
- **缺点**：人力成本最高
- **评估指标**：
  - 客观指标：精准度、召回率、准确率、匹配度
  - 主观指标：连贯性、事实正确性、丰富度、可读性、前后一致性、逻辑流畅度

> 人工评测在当前阶段不会被淘汰。即使成熟的行业（如手机评测）仍有第三方人工测试存在。

### 5.2 基准测试（Benchmark）

- **常用工具**：
  - **LM Eval**（谷歌）
  - **Lighteval**（Hugging Face）
  - **EvalScope**（阿里云，推荐重点学习）

- **常用测试集**：
  - `MMLU`：通用知识（最常用）
  - `C-Eval`：中文版 MMLU
  - `GSM8K` / `ARC`：数学推理
  - `HumanEval`：代码生成
  - `TruthfulQA`：真实性问答

- **使用方法**（以 Hugging Face Lighteval 为例）：

```bash
pip install lighteval
lighteval \
    --model "model-name" \
    --tasks "mmlu,gsm8k" \
    # 会自动下载模型到本地进行评估打分
```

- **使用方法**（以 EvalScope 为例）：

```bash
# 务必使用 conda 安装，避免环境冲突
conda create -n evalscope python=3.10
conda activate evalscope
pip install evalscope

# 运行评估
evalscope --model <model-path> --dataset arc,gsm8k --limit 5
```

结果会输出在 `output/` 目录下，包含各测试集的得分。

### 5.3 大模型作为裁判（LLM as Judge）

当没有标准答案的测试集时（如评估写科幻小说的能力），可以调用一个更大的模型（如阿里云上的 API）来对结果进行打分。

在 EvalScope 中可以通过配置自定义测试集和远程打分模型来实现。

## 6. 开源软件质量评估

### 6.1 评估维度

1. **功能匹配**（压倒一切的前提）— 功能不满足需求则其他无从谈起
2. **性能与开销**
   - 响应速度、并发能力
   - vLLM vs Ollama：并发场景下 vLLM 性能是 Ollama 的 2~10 倍；单用户场景 Ollama 响应略快（约为 vLLM 的 90%）
3. **生命周期与文档**
   - 是否长期维护（三年未更新则慎选）
   - 文档质量反映团队的产品化能力
4. **安全架构**（一票否决项）
5. **稳定与可扩展性**：插件系统、接口设计
6. **二次开发潜力**：官方是否提供了二次开发接口
7. **许可证**：是否允许免费商用

### 6.2 开源生态评估

生态是指一个产品即使其原始创建者"消亡"，仍然有社区能自我修复、延续其生命（如 Java、Linux）。

**值得关注的 AI 生态**：
- **Llama 系列**：代表研究方向，新论文一出，其他模型（如千问）很快跟进
- **Hugging Face**：不仅是模型下载平台，更是完整的 AI 开发生态

## 8. Python 包管理工具一览

### 8.1 发展历程

```
操作系统级包管理（apt/yum）
  → pip + venv（Python 官方）
    → virtualenv（社区方案）
      → conda（管理 Python + 二进制依赖）
        → miniforge（社区免费版，默认使用 conda-forge 频道）
          → uv（新兴整合工具）
```

### 8.2 为什么用 Conda

- 能管理 Python 包以及**非 Python 的二进制依赖**（如 CUDA 工具包）
- 在科学计算和深度学习场景下更为适用
- `miniforge` 是目前最常用的免费发行版

### 8.3 虚拟环境的本质原理

```python
# 未进入虚拟环境时
import sys
print(sys.path)
# 搜索路径指向系统 site-packages

# 进入虚拟环境后
# 搜索路径指向当前目录下的虚拟环境目录
# 系统包全部屏蔽，实现依赖隔离
```

> **最佳实践**：一个项目一个虚拟环境。

## 10. 课程总结与建议

### 10.1 推荐的学习资源

- **Hugging Face 专题视频**（课程预习专栏中）：重点看如何查看模型详情页、如何找数据集
- **吴恩达《机器学习》旧版**（黑板手写版）：适合入门，从线性回归讲起，浅显易懂
- **推荐书籍**（含在课程材料中）：用于系统学习基础理论

### 10.2 项目管理好习惯

- 项目依赖配置文件（`pyproject.toml` / `requirements.txt`）**必须写**
- 版本号**不要只写 `>=`**，至少限定在 `>= A, < B`（小版本内）
- 明确指定版本号，避免坑到自己或他人

### 10.3 常见问题速查

| 问题 | 解决思路 |
|------|----------|
| Unsloth 更新报错 | 回退版本，或关注官方修复 |
| CUDA 未初始化 | 重启内核（Jupyter Notebook 需手动重启） |
| 系统盘爆满 | 将 Hugging Face 缓存目录软链接到数据盘 |
| 模型返回非 JSON | 检查数据集标注质量，确保微调正确 |
| vLLM 启动 OOM | 限制 `--max-model-len` |
| 网络访问 Hugging Face 慢 | 使用国内镜像站或云平台学术加速 |
