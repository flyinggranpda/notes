## 2. 项目总体架构

### 2.1 系统概览

整个系统分为三个主要项目模块：

```
┌─────────────────────────────────────────────────────────────┐
│                    企业知识库系统架构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [管理后台 (Adan Admin)]                                    │
│   └── 上传文件 / 管理文档 / 查看索引状态                     │
│          │                                                  │
│          ▼                                                  │
│  [对象存储 (MinIO / S3)]                                    │
│   └── 存储原始文件 + 向量数据库落盘数据                      │
│          │                                                  │
│          ▼ (文件变化监听)                                    │
│  [索引服务 (Index Service)]                                 │
│   ├── 解析文档 (PDF/Office/Text/Markdown)                   │
│   ├── 文本切片 (LangChain Splitter)                         │
│   └── 向量化 (Embedding API)                                │
│          │                                                  │
│          ▼                                                  │
│  [向量数据库 (Milvus)]                                      │
│   └── 存储向量 + 标量字段，提供相似度检索                     │
│          │                                                  │
│          ▼                                                  │
│  [微信客服 (对外交互)] ← 下节课内容                          │
│   └── 企业微信客服接入，提供RAG问答                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 三个核心项目

| 项目 | 作用 | 关键技术 |
|------|------|---------|
| **Milvus 部署** | 向量数据库 + MinIO 对象存储的 Docker 部署 | Docker Compose, ETCD, MinIO |
| **Adan Admin** | 管理后台，提供文件上传/管理/查看的 Web 界面 | Flask, Python |
| **微信客服** | 对外交互入口，用户通过企业微信客服提问 | 企业微信 API, RAG 流程 |

### 2.3 工作流程

```
1. 用户通过管理后台或 MinIO 客户端上传文件
       ↓
2. MinIO 监听器检测到文件新增
       ↓
3. 索引服务从 MinIO 获取文件
       ↓
4. 文档解析器将文件转译为文本（PDF/Office/Markdown/Text）
       ↓
5. 文本切片（LangChain Splitter）
       ↓
6. Embedding 模型将切片转成向量
       ↓
7. 向量 + 元数据存入 Milvus 向量数据库
       ↓
8. RAG 检索（下节课）→ 用户提问 → 向量检索 → 重排 → 大模型生成回答
```

> 费曼说：整个系统可以理解为一个"文档加工流水线"。文件进来先解析成纯文本，再切成合适大小的片段，每个片段转成向量存进向量数据库。用户提问时，系统把问题也转成向量，去库里找最相似的片段，最后让大模型根据这些片段来回答。这样大模型就不会"乱说"，答案完全基于企业自己的文档。

### 4.3 MinIO 对象存储

**核心概念**：

| 概念 | 说明 |
|------|------|
| **Bucket（桶）** | 存储目录，类似文件系统的根目录 |
| **Object（对象）** | 存储的文件实体，每个对象有一个唯一 Key |
| **Access Key** | 访问密钥 ID |
| **Secret Key** | 访问密钥密码 |

**MinIO 与向量数据库的关系**：

```
Milvus（计算层）— 无状态，不持久化数据
     │ 所有数据存储在
     ▼
MinIO / S3（存储层）— 提供 99.999% 可靠性的对象存储
     │ 存储内容
     ├── Milvus 的索引和数据（序列化为对象）
     └── 用户上传的原始文档
```

- MinIO 兼容 AWS S3 协议，也可替换为阿里云 OSS、AWS S3 等服务
- 这种"存储计算分离"架构是现代软件架构的发展趋势
- MinIO 自带的 Web UI（端口 9001）用于浏览和管理文件

**常用操作**：
- 创建 Bucket（如 `test`）
- 上传/下载文件
- 创建目录
- 查看文件元数据

### 4.4 Milvus 向量数据库

**管理工具（ATTU）**：
- 类似 MySQL 的 Navicat/Workbench
- 连接到 Milvus 的 API 端口（19530）
- 支持可视化创建 Collection、查看数据、执行检索

**Collection（集合）概念**：

Milvus 中的 Collection 类似于关系数据库中的表：

```
Collection（集合）≈ 数据库表
  ├── 向量字段（Vector Field）
  │     └── float vector, binary vector, float16, bfloat16, sparse vector
  ├── 标量字段（Scalar Field）
  │     └── int8/16/32/64, float, string 等标准数据类型
  └── 索引（Index）
        └── 为向量字段建立索引以加速检索
```

**向量维度（Dimension）**：
- 本项目中使用的 Embedding 模型维度为 **768**
- 维度在配置文件中设置，必须与 Embedding 模型输出维度一致

## 6. 索引服务（Index Service）

### 6.1 核心流程

```
MinIO 文件变化
    ↓ (事件通知)
索引服务收到通知
    ↓
获取文件内容（二进制数据）
    ↓
选择文档解析器（根据文件类型）
    ↓
解析为纯文本
    ↓
文本切片（LangChain Text Splitter）
    ↓
调用 Embedding API 生成向量
    ↓
构造文档对象（向量 + 元数据）
    ↓
存入 Milvus 向量数据库
```

### 6.2 监听机制

使用 AWS S3 协议标准的事件通知机制监听 MinIO Bucket 的变化：

```python
# 监听器初始化
from minio import Minio

client = Minio(
    endpoint="127.0.0.1:9000",
    access_key="<access_key>",
    secret_key="<secret_key>",
    secure=False
)

# 注册 Bucket 事件通知
def start_listening(bucket_name):
    # 监听 create 和 remove 事件
    # S3 标准协议事件类型：
    # - s3:ObjectCreated:*  — 文件新增
    # - s3:ObjectRemoved:*  — 文件删除
    pass
```

**事件通知包含的信息**：
- `key` — 文件的完整路径（从根目录开始，如 `目录/文件名.pdf`）
- `eTag` — 文件的 MD5 值（大文件分片上传时 eTag 可能带后缀）
- `bucket` — 所属 Bucket 名称

> **注意**：S3 协议支持版本管理。相同 Key 的对象可以覆盖替换，也可以保留旧版本。在企业环境中建议开启版本管理，确保数据不丢失。

### 6.3 文档解析器架构

采用**策略模式**设计，每种文件类型注册对应的解析器：

```python
# 抽象基类
class BaseParser(ABC):
    @abstractmethod
    def support(self, content_type: str) -> bool:
        """判断是否支持该文件类型"""
        pass
    
    @abstractmethod
    def parse(self, data: bytes) -> str:
        """解析二进制数据为文本"""
        pass

# 解析器注册器
class ParserRegistry:
    parsers = []
    
    @classmethod
    def register(cls, parser):
        cls.parsers.append(parser)
    
    @classmethod
    def get_parser(cls, content_type):
        for parser in cls.parsers:
            if parser.support(content_type):
                return parser
        return None
```

**支持的文档类型**：

| 解析器 | 支持的文件类型 | 使用的库 | 说明 |
|--------|---------------|---------|------|
| **PDF Parser** | `application/pdf` | **PyPDF2** | 从 PDF 中逐页提取文本 |
| **Text Parser** | `text/plain`, `text/html`, `text/markdown` | 内置 | 纯文本/HTML/Markdown 解析 |
| **Office Parser** | Word, Excel, PPT, PDF | **markitdown** (微软) | 微软官方文档解析库 |
| **Miner U** | PDF 及复杂格式 | Miner U (国产开源) | 进阶功能，需要额外算力部署，支持 OCR |

**PDF 解析示例（使用 PyPDF2）：**

```python
import PyPDF2
from io import BytesIO

class PDFParser(BaseParser):
    def support(self, content_type):
        return content_type == "application/pdf"
    
    def parse(self, data):
        text = ""
        reader = PyPDF2.PdfReader(BytesIO(data))
        for page in reader.pages:
            text += page.extract_text() + "\n"
        return text
```

> 费曼说：解析器就像"万能钥匙"。不同格式的文件要用不同的"钥匙"来打开。PDF 文件需要逐页提取文字，Office 文件微软自己有专门的库，纯文本最简单直接读就行。设计成插件式的好处是——以后要支持新格式，只需加一个新的解析器类，注册进去就行。

## 7. 向量数据库核心概念

### 7.1 数据类型

Milvus 支持多种向量数据类型：

| 类型 | 说明 | 常见用途 |
|------|------|---------|
| `FLOAT_VECTOR` | 标准浮点向量 | 文本 Embedding（最常用） |
| `BINARY_VECTOR` | 二进制向量 | 高效存储和快速匹配 |
| `FLOAT16_VECTOR` | 半精度浮点向量 | 节省存储空间 |
| `BFLOAT16_VECTOR` | 脑浮点向量 | 大模型训练常用精度 |
| `SPARSE_VECTOR` | 稀疏向量 | 关键词匹配场景 |

### 7.2 索引类型

| 索引类型 | 原理 | 特点 |
|---------|------|------|
| **FLAT** | 全量扫描，不建索引 | 精确度最高，速度最慢（类似 MySQL 全表扫描） |
| **IVF_FLAT** | K-Means 聚类分组，在组内搜索 | 速度快，精度可接受，最常用 |
| **HNSW** | 分层可导航小世界图 | 搜索极快，索引构建较慢 |

### 7.3 IVF_FLAT 索引详解

**工作原理**：

```
1. 建索引阶段（K-Means 聚类）：
   所有向量 → 分成 N 组（如 128 组）→ 每组有一个中心点
   
2. 搜索阶段：
   查询向量 → 计算与各组中心点的距离 → 选出最接近的 N 组（nprobe 参数）
   → 只在选中的组内进行精确搜索 → 返回 Top-K 结果
```

**关键参数**：
- `nlist` — 建索引时聚类分组的数量（如 `nlist=128`）
- `nprobe` — 搜索时查询的组数（如 `nprobe=64`，值越大精度越高，速度越慢）

**IVF 设计理念**：把"整理数据"的工作放在索引阶段，把"高效检索"留给搜索阶段。

### 7.4 度量方法（相似度算法）

| 度量方法 | 公式本质 | 范围 | 适用场景 |
|---------|---------|------|---------|
| **余弦相似度 (Cosine)** | 计算向量夹角余弦值 | `[-1, 1]` | 文本相似度（最常用） |
| **内积 (IP / Inner Product)** | 向量在另一向量上的投影长度 | `[0, 1]` | 与余弦本质一致 |
| **欧式距离 (L2)** | 多维空间的直线距离（勾股定理扩展） | `[0, +∞)` | 图像/视觉特征 |
| **Jaccard 距离** | 交集/并集比率 | `[0, 1]` | 集合相似度 |

> 费曼说：这些相似度算法就是判断两个向量"像不像"的不同方法。余弦相似度看方向是否一致（角度越小越像），欧式距离看位置是否接近（距离越短越像）。文本检索最常用余弦相似度。

### 7.5 HNSW 索引（分层可导航小世界）

- 将向量按层级组织，上层是粗粒度分组，下层是细粒度分组
- 各组之间用图结构关联
- 搜索时从粗到细逐层精确定位
- 类似于"跳表"的思想

### 9.2 索引服务核心逻辑

```python
# 伪代码：核心处理流程
def handle_event(event):
    """处理 MinIO 文件变更事件"""
    # 1. 解析事件信息
    bucket = event.bucket
    key = event.key  # 文件完整路径
    action = event.action  # create / remove
    
    if action == "create":
        # 2. 从 MinIO 获取文件
        data = get_object(bucket, key)
        
        # 3. 确定文件类型
        content_type = get_content_type(key)
        
        # 4. 选择解析器
        parser = ParserRegistry.get_parser(content_type)
        if not parser:
            return
        
        # 5. 解析文本
        text = parser.parse(data)
        
        # 6. 文本切片
        chunks = text_splitter.split_text(text)
        
        for chunk in chunks:
            # 7. 向量化
            vector = embedding_client.embed(chunk)
            
            # 8. 构建文档对象并存入 Milvus
            doc = Document(
                doc_name=key.split("/")[-1],
                doc_path=key,
                content=chunk,
                vector=vector,
                ...
            )
            milvus_client.insert(doc)
    
    elif action == "remove":
        # 删除对应的向量记录
        milvus_client.delete_by_path(key)
```

## 10. 对比与总结

### 10.1 三种向量数据库部署模式对比

| 维度 | Local（本地） | 分布式 | 可选（云 OSS） |
|------|-------------|--------|---------------|
| **部署复杂度** | 低（一键 Docker） | 高（需要 K8s 环境） | 中 |
| **数据持久性** | 依赖本地磁盘 | 高（S3 协议 99.999%） | 高（云厂商保障） |
| **使用场景** | 开发测试 | 企业正式环境 | 企业正式环境 |
| **横向扩展** | 不支持 | 支持 | 支持 |
| **推荐度** | ⭐ 上手指南 | 进阶 | 灵活方案 |

### 10.2 三种索引类型的性能权衡

| 索引类型 | 索引构建速度 | 搜索速度 | 内存占用 | 精度 |
|---------|------------|---------|---------|------|
| **FLAT** | 无索引（快） | 慢（全量扫描） | 低 | 最高 |
| **IVF_FLAT** | 中（需 K-Means） | 快 | 中 | 较高（取决于 nprobe） |
| **HNSW** | 慢（建图耗时） | 极快 | 高 | 高 |

### 10.3 知识库完整构建流程

```
[准备阶段]
选服务器（阿里云 ECS）→ 配远程开发环境（Cursor）→ 安装 Docker → 安装 Conda

[部署阶段]
启动 Milvus + MinIO（Docker Compose）→ 配置 ATTU 管理工具 → 创建 Bucket 和 Collection

[开发阶段]
配置管理后台 → 启动 Flask 服务 → 配置索引服务 → 测试文件上传 → 验证索引流程

[应用阶段]
接入 Embedding 服务（阿里云百炼/硅基流动）→ 全量刷新文档 → 增量监听模式 → 对外提供 RAG 服务
```

### 10.4 关键经验总结

1. **存储计算分离是趋势** — Milvus 只做计算，数据持久化交给 MinIO/S3，这种架构便于横向扩展
2. **兼容 OpenAI 协议** — 选择 Embedding 和 LLM 服务时优先选兼容 OpenAI 协议的，便于迁移和切换
3. **永远准备备用方案** — Embedding 服务和 LLM 服务都要有备选供应商
4. **建索引慢但只见一次** — 全量刷新耗时较长，但之后增量更新非常快
5. **解析器插件化设计** — 便于扩展新的文件格式支持
6. **SSH 端口转发非常实用** — 有 SSH 权限就能访问服务器上的任何端口，比配防火墙方便得多
