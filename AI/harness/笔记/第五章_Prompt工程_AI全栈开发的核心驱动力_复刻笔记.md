## Part 1 项目介绍与 Prompt 认知（5-1、5-2）

### 5-1 项目整体介绍：WanderChina

**Step 1 明确项目创意来源（两个事实）**

| 事实 | 内容 |
|---|---|
| 市场现象 | 抖音/YouTube 上"外国人来中国旅游被震撼"视频爆火（高铁 350km/h、扫码支付、深夜撸串），播放量动辄千万，产生大量来华意愿 |
| 信息鸿沟 | 外国游客来华前后面临三大困难：①无英文版"大众点评"（查景点无门）②无专属社区（问"北京3天怎么玩"只能去 Reddit 发帖等慢回复）③途中问题（点菜看不懂、买票不会）无即时帮助 |

**Step 2 明确项目目标（三位一体）**

- 旅游社区：外国游客互相交流经验
- 景点攻略：把分散信息整理成结构化内容
- AI 助手：实时问答，解决点菜、购票、交通等即时问题
- 本章核心任务：**通过 Prompt 工程，把这份产品需求文档（PRD）用 AI 写出来**

**Step 3 体感差距：同一个创意，两种 Prompt**

| 维度 | Prompt A（多数人写法） | Prompt B（本章教你写的） |
|---|---|---|
| 原文 | "帮我做一个外国人来中国旅游的网站。" | `[R]` 精通社区产品+入境旅游的产品经理，偏好MVP思维<br>`[C]` 144免签/入境增长30%+/技术栈Next.js+Spring Boot+MySQL<br>`[T]` 输出MVP方案：模块清单(≤6) + User Flow + WHEN/THEN验收<br>`[约束]` 3周/1人+AI；不做支付/酒店；Markdown格式 |
| AI 输出 | 泛泛描述，无模块划分、无验收标准、无法开工 | 结构化需求文档，各模块定义清晰，可直接开工 |

**核心结论**：`你的 Prompt 能力上限 = 你用 AI 的能力上限`。同样的模型，产出质量差十倍，差距完全取决于你给 AI 的信息质量。
类比：跟服务员说"随便来点好吃的" vs "宫保鸡丁，微辣，花生少点，米饭少点"。

### 5-2 Prompt 基础认知与重要性

**Step 1 认知转变：Prompt = AI 开发中的编程语言**

| | 传统开发 | AI 开发 |
|---|---|---|
| 流程 | 人写 Java 代码 → 编译器执行 → 产出软件 | 人写 Prompt → AI 执行 → 产出软件 |
| 出问题时 | 问题出在代码 | 问题往往出在"代码"（Prompt）本身，而非 AI |

易混点：不要把"Prompt 质量差"误判为"AI 能力不足"。

**Step 2 理解 Prompt 驱动 SDD 五阶段（每步的输入都是 Prompt）**

| SDD 阶段 | 人做什么 | Prompt 驱动 AI 做什么 | 产出制品 |
|---|---|---|---|
| Specify（需求定义） | 定义需求边界 | 市场调研、产出产品规格 | Product Spec |
| Plan（技术设计） | 确认技术方向 | 架构设计、技术选型 | 技术方案 |
| Tasks（任务拆解） | 拆分优先级 | 分解任务、排定 Sprint 计划 | Sprint 计划 |
| Implement（代码实现） | 审核代码质量 | 生成功能代码（API/DDL/前端组件） | 功能代码 |
| Verify（验收） | 判断是否通过 | 代码 Review、安全审计、生成测试用例 | 验收报告 |

分工原则：**人负责决策（选方向、画边界、审结果），AI 负责执行**。每个阶段需要独立 Prompt，不是一次性完成。

**Step 3 理解乘法关系（不是加法）**

- 60 分 Prompt：0.6 × 0.6 × 0.6 × 0.6 × 0.6 = **7.8%**
- 90 分 Prompt：0.9 × 0.9 × 0.9 × 0.9 × 0.9 = **59%**
- 差距 **7.5 倍**。花 15 分钟打磨 Prompt，可避免后面两天的返工
- 比喻：地基挖了 10 厘米，到楼顶就会歪 1 米——Prompt 质量影响的不止当前这一步，而是后续每一步

**Step 4 掌握 RCTC 四层认知架构（高质量 Prompt 的底层结构）**

| 层 | 要素 | 作用 | 关键规则 |
|---|---|---|---|
| R | Role 角色 | "你是谁"，激活特定领域知识 | 分三级：L1 职业身份 → L2 +技能域 → L3 +行为约束。定义"产品经理"→AI 关注用户价值；定义"后端架构师"→AI 关注性能扩展性。黄金法则：像去医院挂号，告诉 AI"挂哪个科" |
| C | Context 上下文 | "现在什么情况"，**影响输出质量最大的要素** | 信息量 = 给新同事做项目交接时的信息量。少了 AI 瞎猜，多了 AI 迷失重点 |
| T | Task 任务 | "交付什么"，锁定输出目标 | 三标准：产出物明确、可分解、可验收。对比："帮我分析竞品" vs "输出竞品分析报告，含五个竞品的优劣势对比" |
| C | Constraints 约束 | "什么能做不能做"，画行为边界 | 四维度：技术约束、范围约束、格式约束、行为约束。不说"三周内完成"，AI 可能设计出需要六个月的项目 |

**质量公式**（乘法，任一为 0 则总输出归零）：

```
AI输出质量 = R精准度 × C完整度 × T明确度 × 约束可执行度
```

**Step 5 RCTC 快速示例（创意调研）**

- 反面 Prompt A："帮我做一个外国人来中国旅游的网站" → R=0、C≈0、T 模糊、C=0，四项全零，产出≈0
- 正面 Prompt B（四层齐全）：
  - R：你是专注入境旅游市场的产品分析师（激活旅游+产品双重知识）
  - C："外国人来中国旅游"趋势爆火，144免签，想做社区+AI平台（刚好够用的背景）
  - T：输出结构化调研报告：趋势数据+痛点地图+竞品不足+切入方向（明确产出物）
  - 约束：每维度一节、关键数据加粗、Markdown格式（锁定格式和行为边界）
- 结果：AI 知道用什么视角、在什么背景下、产出什么形态、边界在哪，无需猜测

**核心认知迁移**：最值钱的能力不是写代码，而是写 Prompt——代码可交给 AI，但"告诉 AI 写什么"只能由人完成。

## Part 2 Prompt 构建原则与分类（5-3）

### 三条铁律

**Step 1 铁律一：信息分层，渐进投喂**

- 核心问题：一次性给 AI 太多需求（如 6 个模块）→"注意力稀释"，每个需求只能做到 50 分
- 硬性规则：**Prompt 超过 200 字必须分层，每层只传递 1 个核心信息，确认后再给下一层**
- 操作口诀："一次一件事，确认再下一层"（像引导飞行员降落，一条指令一次确认）

| | 反例 | 正例（分层投喂） |
|---|---|---|
| 做法 | 一口气要求"设计6个模块的完整Spec，包含User Flow、验收标准、数据模型…" | 第一层："6个模块，先给文档大纲。"→ 确认方向<br>第二层："展开社区论坛模块的详细Spec。"→ AI 集中精力做到90分<br>第三层："给这个Spec加上验收标准和数据模型。"→ 质量可控 |
| 结果 | 每个模块50分，没有一个90分 | 每层一个焦点，质量逐层可控 |

**Step 2 铁律二：验收标准给样本（Example 代替描述）**

- 核心问题："具体一点""专业一点""详细一点"这类形容词是**毒药**——AI 和你对这些词的理解完全不同
- 解决方案：别说形容词，直接给一个样本。AI 是模式匹配大师：给模式它能复制，给文字描述它只能猜
- 记忆点："形容词是毒药，Example 是解药"；一个好样本 > 100 行文字描述

```
反例：验收标准要具体可执行
      → AI理解的"具体"跟你想的可能完全不同

正例：验收标准按此格式：
      WHEN 用户按城市筛选景点列表
      THEN 2秒内返回该城市所有景点
      AND 按评分降序排列
      请按此格式为其他模块编写。
```

**Step 3 铁律三：约束渐进收紧**

- 核心问题：一上来就把约束拉满（"只能做简单聊天，不能检索数据"）→ 杀死 AI 可能提出的高价值方案（如 RAG 检索），好想法永远不会出现
- 正确节奏：**三轮渐进收紧**，"先让 AI 飞，再慢慢收缰绳"——约束是缰绳，不是笼子

| 轮次 | 松紧 | 示例 | 效果 |
|---|---|---|---|
| 第1轮 | 宽松（看AI天花板） | "设计AI助手功能，不限制能力边界。" | AI 建议 RAG+多轮对话+知识图谱 |
| 第2轮 | 中等（收窄方向，不锁死细节） | "只保留RAG和多轮对话，去掉知识图谱。" | 方向收窄 |
| 第3轮 | 严格（锁死边界，确保不越界） | "RAG只索引景点+美食，禁止连接外部API。" | 边界锁死 |

### 四种编程场景的 Prompt 姿态

**Step 4 掌握核心原则**：好的 Prompt 不是一种模板用到底，而是根据项目阶段切换对话姿态。**越往项目后期，约束越紧，AI 自由度越小**。类比开车：高速（自由选车道）→ 城区（限速）→ 停车入位（毫米级精度）。

**Step 5 四种姿态速查表**

| 场景 | 姿态 | 使用时机 | 核心句式 | RCTC 配置 | 目的 |
|---|---|---|---|---|---|
| 需求探索 | 发散型 | 项目初期：调研市场、分析痛点、头脑风暴 | "有哪些可能？""从多个维度分析" | 角色精准 + 任务开放 + 约束宽松 | 画认知地图，看清领域全貌，不是直接给答案 |
| 方案设计 | 收敛型 | 调研完毕：锁定MVP范围、技术选型、定架构方向 | "基于以下约束输出方案""二选一给理由" | 角色精准 + 上下文丰富 + 约束中等 | 画围栏，让 AI 在围栏内找最优解 |
| 代码生成 | 精确型 | 方案确定，开始写代码 | "严格按照Spec实现，禁止越界""按此格式输出" | 上下文最丰富 + 任务最明确 + 约束最严格（自由度≈0） | 给图纸，AI 照图施工。请求路径、校验规则、权限、响应码全部写死 |
| 质量验证 | 对抗型 | 代码写完：Review、安全审计、找漏洞 | "帮我找出所有问题""假设你是黑客""禁止说总体不错" | 角色 = 挑战者/攻击者 | 让 AI 唱反调，免费的安全审计专家 |

**四种姿态横向对比**

| 对比维度 | 需求探索 | 方案设计 | 代码生成 | 质量验证 |
|---|---|---|---|---|
| AI 自由度 | 最高（发散探索） | 中等（框定范围） | 最低（照图施工） | 中等（对抗挑战） |
| 约束强度 | 宽松 | 中等 | 严格 | 中等 |
| 核心目标 | 看清全貌 | 锁定最优解 | 精确执行 | 发现漏洞 |
| 项目阶段 | 项目初期 | 调研完成后 | 方案确定后 | 代码完成后 |
| 容错空间 | 最大 | 中等 | 最小 | 中等 |

**使用节奏**：发散（前期）→ 收敛（中期）→ 精确（后期）→ 对抗（收尾）

**Step 6 三个项目实战示例（直接抄）**

收敛型（方案设计）——画围栏，给 AI 决策空间：

```
基于以下约束确定MVP模块清单：
- 目标用户：25-45岁自由行外国游客
- 开发周期：3周/1人+AI
- 技术栈：Next.js + Spring Boot + MySQL + Spring AI
- 排除：不做支付/酒店预订
输出：模块清单(6个以内) + 优先级 + 一句话价值主张
```

精确型（代码生成）——AI 自由度接近零，给的是图纸：

```
严格按照以下Spec实现社区帖子的创建API：
- POST /api/posts
- 请求体：{ title, content, cityTag, images[] }
- 校验：title 5-100字符，content 10-5000字符，images≤9张
- 权限：仅USER和ADMIN角色可调用
- 响应：201+帖子完整对象 / 400参数错误 / 403无权限
- 约束：Controller只做参数校验+调Service，禁止写业务逻辑
输出Java代码，含Controller + Service接口。
```

对抗型（质量验证）——故意让 AI 唱反调：

```
你是一位严苛的安全工程师。
Review WanderChina的权限管理设计，假设你是恶意用户：
- 普通用户能否通过修改请求访问管理员接口？
- 帖子作者能否删除别人的帖子？
- JWT过期后能否继续访问受保护资源？
每个漏洞给严重程度(P0/P1/P2)和修复建议。
禁止说"总体设计合理"——我只要问题和修复方案。
```

## Part 3 Prompt 优化与迭代技巧（5-4）

**前提认知**：第一版 Prompt 永远是半成品。拉开差距的不是谁能一次写对，而是谁**知道怎么改**。
常见误区：AI 输出不好就删掉整个 Prompt 从头重写——如同感冒了不查病因直接换医院挂号。

**Step 1 看病四步法：先诊断，对症下药**

| 症状 | 病因 | 药方 |
|---|---|---|
| AI 答非所问，跑偏了 | Context 不够 | 补角色+背景：告诉 AI"你是谁、在什么情况下做事" |
| 输出太泛，不落地 | Task 太模糊 | 加验收标准：用 WHEN/THEN 格式锁死产出物 |
| 质量时好时坏 | 约束缺失 | 补格式+边界约束：画好围栏，不让 AI 乱跑 |
| 一本正经胡说八道 | AI 在"编" | 加"只基于以下信息回答"：关掉脑补能力 |

实战案例（WanderChina 帖子 API）：

| | Prompt | 结果 |
|---|---|---|
| 翻车 | "帮我设计帖子模块的REST API" | AI 输出通用博客系统 API，跟旅游社区无关 → 诊断为"答非所问"，Context 不够 |
| 修复 | 加上 [R]精通Spring Boot的旅游社区工程师 + [C]面向外国游客、需要城市标签+多语言+图片上传 | API 立刻有 cityTag 字段、i18n 支持、Multipart 图片上传 |

核心原则：先诊断是哪种"病"，对症下药，改一两句话就能救回来。

**Step 2 增量修补法：外科手术式修改，别推翻重来**

原则：改 Prompt 跟做手术一样，**切口越小，恢复越快**。

| 步骤 | 动作 | 说明 |
|---|---|---|
| ① 先夸一句 | 告诉 AI"哪些做得好" | 锁定正确方向（改作业先说哪里写对了，学生才知道哪些该保留） |
| ② 只改痛点 | 用最精确的 1-2 句话描述哪里不对 | 不是重写整篇文章，是改那个错别字 |
| ③ 给个参照 | 用一个 Example 告诉 AI 你想要什么样 | 像给装修师傅看一张参考图，比"弄得高级一点"管用百倍 |

实战示例（AI 生成了帖子创建 API，结构不错但缺参数校验）：

```
1. 夸："API结构很好"
2. 改："但缺少参数校验，请补充：title 5-100字符、content 10-5000字符、images≤9张"
3. 参照："参考格式：@Size(min=5, max=100) String title"
效果：AI 只补校验逻辑，不破坏已有的正确代码结构
```

**Step 3 版本对比法：迭代不靠"感觉"，靠数据**

陷阱：改了 Prompt 跑一遍，觉得"好像比上次好了"就用了——**"好像"两个字最危险**。

三个评估维度（每维度打 1-5 分）：

| 评估维度 | 评估标准 | 示例旧分→新分 |
|---|---|---|
| 完整性 | 能否覆盖所有需求点？ | 3 → 4 |
| 准确性 | 有没有胡说八道？ | 3 → 5 |
| 可执行性 | 开发拿到能不能直接用？ | 2 → 4 |
| **总分** | **13 分以上 = 迭代有效** | 9 → 13 |

操作步骤：
1. 每次改 Prompt，把新旧输出放在一起
2. 三个维度各打 1-5 分，记录在手机备忘录
3. 总分上升但某个维度降分 → 说明改过头了，回退一步
4. 警惕"按下葫芦浮起瓢"：完整性提升，准确性可能下降——没有对比表根本发现不了

**Step 4 建 Prompt 零件库：高手不是写得好，是攒得多**

类比乐高：单个积木没什么用，攒到 50 块、100 块，拼什么都能很快。

| 分类 | 模板示例 |
|---|---|
| 角色模板（R层定义） | "你是精通Spring Boot + Spring AI的后端工程师，代码风格参考Google Java Style" |
| 验收模板（WHEN/THEN标准） | "WHEN用户请求帖子列表 THEN返回分页数据 AND按创建时间倒序" |
| 约束模板（技术约束） | "使用Java 17、Spring Boot 3.2，禁止使用Lombok，统一ResponseWrapper" |
| Review模板（对抗型审查） | "假设你是恶意用户，检查以下接口是否存在越权访问风险，标注P0/P1/P2" |

实战效果：**70% 的 Prompt 从零件库拿出来改改就能用**——不是懒得写，是踩过的坑、验证过的模板比从头写靠谱得多。

**Step 5 迭代飞轮（本章方法论总收口）**

```
写 → 测 → 改 → 存（存入零件库）→ 再写……
```

1. 看病四步法：答非所问补 Context / 太泛加验收 / 波动补约束 / 胡编加限制
2. 增量修补法：先夸 → 只改痛点 → 给 Example 参照
3. 版本对比法：三维度打分，13 分以上 = 有效迭代
4. Prompt 零件库：角色/验收/约束/Review 四类模板，攒得越多拼得越快

**Prompt 工程的终点不是"写出一版完美的 Prompt"，而是建起一套"写→测→改→存"的迭代飞轮。飞轮转起来，AI 输出质量越滚越高。**

## Part 4 完整实战：模糊创意 → 结构化需求文档（5-5）

**实战目标**：通过几轮 Prompt 对话，把模糊的"外国人来中国旅游"创意，逐步转化为可开工的 MVP 模块清单。使用工具：Qwen（通义千问）。
方法论：围绕 RCTC 架构，按"发散 → 收敛 → 精确"三轮对话落地。**每一轮的输出都是下一轮的输入**。

**Step 1 第一轮：发散型需求调研（对应 SDD 阶段 Specify）**

你的角色：探索者；AI 的角色：分析师；约束：宽松；产出：认知地图。
目的：做市场调研，验证"这个事情能不能做"。

Prompt 设计（RCTC）：
- R："专注入境旅游市场的资深产品分析师"
- C：YouTube/TikTok 上"外国人来中国旅游被震撼"视频爆火；144 小时过境免签政策；外国游客面临信息鸿沟
- T：输出结构化调研验证报告，四个维度：市场机会、痛点地图、竞品分析、切入建议
- 约束：每维度独立成段、Markdown 格式、给出明确 GO/NO-GO 判断及理由

AI 产出要点（四个维度）：

| 维度 | 关键结论 |
|---|---|
| 市场机会 | 入境游处于结构性增长周期：2025 全年入境旅客 1.545 亿人次（+17%），消费总额破 1300 亿美元，免签入境 3008 万人次（+49.5%）；免签已统一延长至 240 小时、适用 55 国。核心用户"过夜自由行旅客"约 3000-4000 万人次/年，信息服务市场空间 3-12 亿美元/年。时机窗口：供给侧（英文数字服务）严重滞后，基础设施缺口 18-24 个月内会被填补 |
| 痛点地图 | ①数字支付鸿沟（外卡绑定失败场景多）②语言与信息壁垒（中文旅游信息丰富但"看得见吃不着"）③预订与出行障碍（12306 英文体验差、景区预约依赖微信小程序、部分酒店不接待外宾）④实时问题无人可问 ⑤文化认知差异（文化翻译服务完全空白） |
| 竞品分析 | TripAdvisor/Lonely Planet：内容覆盖率低、信息滞后、无实时交互（只是"黄页"不是"活地图"）；小红书/马蜂窝/大众点评：信息最鲜活但从设计之初就没考虑外国用户（全中文、需中国手机号）；Trip.com：解决了"订"，没解决"选"和"问" |
| GO/NO-GO | **GO**（值得做），但需精准切入姿势。支撑：需求真实规模可观、供给侧结构性空白（"英文产品有框架没内容，中文产品有内容没接口"）、AI 创造不对称优势。风险：大厂跟进（护城河靠社区深度+AI训练数据）、政策合规、变现路径不确定。建议：AI 实时助手为矛、结构化内容为盾、社区为长期壁垒，先用最小 MVP（能回答中国旅游问题的英文 AI Chatbot）验证获客与留存 |

**Step 2 第二轮：收敛型产品大纲（对应 SDD 阶段 Plan）**

你的角色：决策者；AI 的角色：产品经理；约束：中等；产出：产品轮廓。
信息分层技巧：**把第一轮的输出作为上下文喂给 AI，不是从零开始**。

Prompt 设计（RCTC）：
- R："精通社区产品和入境旅游的产品经理，偏好 MVP 思维"
- C：基于第一轮调研结论（方向已验证、核心痛点 TOP3、切入方向、技术栈、参考竞品不足）
- T：输出产品整体大纲：产品定位 + 目标用户画像 + MVP 功能模块
- 约束：①MVP 模块 ≤6 个 ②开发周期 3周/1人+AI ③本期不做支付/酒店预订/机票比价 ④每个模块功能点 ≤5 个

AI 产出要点：

| 产出 | 内容 |
|---|---|
| 产品定位 | 名称：ChinaCompass。一句话定义：外国游客的"AI中国旅行搭子"。核心价值公式：中文互联网深度信息 × AI 跨语言实时能力 = 外国游客的"随身本地通"。本期只做"信息"和"帮助"，解决"不知道、不会做、问不了" |
| 用户画像A | TikTok 种草型首访者：25-35 岁欧美用户，刷到"China Travel"视频决定来华，零中文基础。诉求：随时用听得懂的语言回答在中国遇到的任何问题 |
| 用户画像B | 240 小时过境探索者：30-45 岁商旅/数字游民，停留 5-10 天，时间紧想高效玩。诉求：最短时间搞懂"怎么从A到B""哪里值得去""怎么预约" |
| 用户画像C | 在华外教/留学生/商务客的"翻译器"：22-40 岁，日常翻译软件凑合，但需要语境和文化解释。诉求：帮我"理解"中国，告诉背后的 why 而不只是 what |

六个 MVP 模块（设计原则：AI 助手是核心引擎，其他模块围绕它展开，不做孤立功能岛）：

| 模块 | 优先级 | 一句话价值 |
|---|---|---|
| AI Travel Assistant | P0（产品灵魂） | 随时用英文问任何中国旅游问题，秒级获得可执行的回答 |
| Survival Toolkit | P0 | 解决"此刻就卡住了"的高频场景：支付、点餐、交通 |
| City Guide Hub | P1 | 按城市浏览结构化英文攻略，不用翻论坛找信息 |
| Community | P1 | 看到其他游客的真实经验，提出 AI 回答不了的问题 |
| User Profile & Trip Board | P2 | 收藏有用信息，生成可分享的行程卡片 |
| Smart Itinerary Builder | P2 | AI 根据时间和偏好自动生成行程草案 |

模块一（AI Travel Assistant）功能点示例：
1. 英文自由问答：基于中国本地知识库返回结构化回答
2. 图片识别问答：拍照上传菜单/路牌，AI 识别中文并英文解释
3. 场景化快问：首页预设高频问题按钮（如"How to pay?"）一键触发
4. 对话上下文保持：单次会话内记住上下文
5. 回答质量反馈：每条回答下方 Helpful/Not helpful 按钮，用于优化 Prompt 和知识库

技术要点：使用 Spring AI 对接大模型，构建中国旅游领域的 RAG 知识库。

**Step 3 第三轮：精确型 Spec 产出（对应 SDD 阶段 Tasks）**

你的角色：图纸师；AI 的角色：技术文档员；约束：严格；产出：可执行的开发 Spec（数据模型、验收标准、依赖关系）。

Prompt 设计要点：
- R：技术产品经理
- T：输出 MVP 模块规格：边界定义 + 用户故事 + 验收标准 + 数据模型
- 约束（最紧）：只做 RAG 景点问答、社区只做帖子 CRUD、首页无个性化推荐
- 验收标准示例：AI 助手——用户输入英文问题，5 秒内返回结构化回答，含信息来源标注；无匹配时明确告知（通用聊天被排除，只做景点攻略问答）

**Step 4 三轮对话总结（一张表收口）**

| | 第1轮 发散 | 第2轮 收敛 | 第3轮 精确 |
|---|---|---|---|
| 你的角色 | 探索者 | 决策者 | 图纸师 |
| AI 的角色 | 分析师 | 产品经理 | 技术文档员 |
| 约束松紧 | 宽松 | 中等 | 严格 |
| 产出 | 认知地图 | 产品轮廓（技术栈、周期、模块优先级） | 可执行 Spec（数据模型、验收标准、依赖关系） |
| 对应 SDD | Specify | Plan | Tasks |

三条核心原则：
1. **渐进投喂**：每一轮的输出都是下一轮的输入，信息分层传递
2. **约束逐轮收紧**：先让 AI 飞一会儿，再慢慢收紧缰绳
3. **控制力增强**：越往后 AI 自由度越小，你对最终产出的把控越精准
